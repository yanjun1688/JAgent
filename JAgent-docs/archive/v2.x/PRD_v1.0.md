# PRD: JAgent 多轮对话与执行鲁棒性提升

> **版本**: v1.0
> **状态**: Draft
> **产品经理**: AgentX
> **日期**: 2026-07-03
> **来源**: `agent_execution_audit_20260703(1).md` — Agent 执行深度审计报告

---

## 1. 执行摘要

JAgent 的架构设计方向正确（事件溯源、受信/非受信分离），但当前产品在**多轮对话体验**上存在根本性缺失。用户每次输入创建一个全新的、独立的 Run，前后两次输入之间共享零上下文。这是导致"不好用"的核心根因。

本 PRD 定义了一个 5 阶段的产品路线图，从最小可行多轮对话到持久化对话记忆，系统性解决多轮场景下的用户体验和执行鲁棒性问题。

---

## 2. 问题分析

### 2.1 用户痛点

| 用户行为 | 当前实际效果 | 用户期望 |
|----------|-------------|---------|
| "帮我查一下东京天气" → "用中文总结" | Run#2 不知道要总结什么 | Agent 记住前一轮结果，正确总结 |
| "今天有什么新闻？" → "详细说第一条" | Run#2 完全不知道"第一条"是什么 | 保留对话历史，能引用前一轮结果 |
| 连续追问 3 轮 | 3 个完全独立的 Run，Agent 每次都从零开始 | 一个连续的对话线程 |
| F5 刷新页面 | 对话丢失，只能看到 Run 列表 | 恢复之前的对话 |
| Agent 执行超出预期 | 无有效手段干预 | 能中断/暂停正在执行的 Agent |

### 2.2 根因

1. **架构层面**：只有 `Run`（单次任务执行）的概念，没有 `Session`/`Conversation`（多轮对话线程）的概念。`Run` 是执行单元，不是对话单元。
2. **前端层面**：`ChatDrawer` 是 V0.3 阶段的"快速演示"组件，一个输入框 + 一个 Run 显示，从未演进为真正的聊天 UI。
3. **后端层面**：`EventStore` 只有 `run_id` 维度的查询，无法跨 Run 查询"某个对话的所有 Run"。
4. **系统 Prompt 层面**：无对话级系统指令，Agent 每轮都重新认识用户意图。
5. **控制层面**：RunMonitor 只能"建议"不能"强制"，无限循环时无法熔断。

### 2.3 数据洞察（定性评估）

- 超过 80% 的用户交互是 2 轮以上的连续追问
- 单轮对话仅覆盖"一次性查询"场景（如"谁是爱因斯坦"）
- 复杂任务（数据分析、多步调研）天然需要多轮交互

## 3. 用户角色

| 角色 | 描述 | 核心需求 |
|------|------|---------|
| **终端用户** | 通过聊天界面与 JAgent 交互的普通用户 | 自然的多轮对话、对话历史可回溯、Agent 能记住上下文 |
| **运维人员 (Operator)** | 监控 Agent 执行，需要干预能力的用户 | 实时查看执行状态、中断/暂停异常 Agent、手动注入反馈 |
| **开发者** | 集成 JAgent 到自有系统的工程师 | 明确的对话级 API、事件流可订阅、会话管理可编程 |

---

## 4. 产品目标

### 4.1 目标

1. **多轮对话**：用户能在同一对话中连续发消息，Agent 自动引用前一轮上下文
2. **对话持久化**：刷新页面后对话不丢失，可恢复历史对话
3. **对话管理**：用户可查看、搜索、删除历史对话
4. **执行可控**：Operator 能中断/暂停异常 Agent 执行
5. **体验流畅**：用户无需等待 Run 完成即可输入下一条消息

### 4.2 非目标

- 本版本不实现对话级向量记忆（跨 Session 的长期记忆）
- 本版本不实现多模态输入（图片/文件上传）
- 本版本不实现对话分支（同一个对话分叉出多个子对话）
- 本版本不实现多人协作对话

## 5. 功能需求

### 5.1 P0: 最小可行多轮对话（Phase 1）

#### F-001: 后端对话模型

| 字段 | 说明 |
|------|------|
| `conversation_id` | 对话唯一 ID |
| `title` | 对话标题（由第一条消息自动生成） |
| `created_at` | 创建时间 |
| `updated_at` | 最后活动时间 |
| `status` | `active` / `archived` |
| `message_count` | 消息总数（冗余，用于列表排序） |

**关联规则**：
- 一个 Conversation 包含 1~N 个 Run
- 每个 Run 关联且仅关联一个 Conversation
- CreateRun 接口接受可选 `conversation_id` 参数

#### F-002: 对话级事件

| 事件 | 触发时机 | Payload |
|------|---------|---------|
| `ConversationStarted` | 对话创建时 | `conversation_id`, `first_message` |
| `ConversationMessage` | 用户发送消息时 | `conversation_id`, `message`, `run_id` |
| `ConversationEnded` | 对话结束时 | `conversation_id`, `summary` |

#### F-003: 对话上下文注入

当用户在已有对话中发送新消息时，后端自动将前几轮的对话摘要注入到新 Run 的 System Prompt 中：

```
System Prompt 结构:
[Base System Prompt]
[对话摘要: 前 N 轮的关键信息]
[当前意图: 用户的新消息]
```

**对话摘要包含**：
- 前几轮的用户意图摘要
- 前几轮的 Agent 主要结论
- 执行过程中出现的错误/警告

#### F-004: API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/v1/conversations` | 创建新对话 |
| `GET` | `/api/v1/conversations` | 获取对话列表 |
| `GET` | `/api/v1/conversations/{id}` | 获取对话详情（含消息列表） |
| `POST` | `/api/v1/conversations/{id}/messages` | 在对话中发送消息（自动创建 Run） |
| `DELETE` | `/api/v1/conversations/{id}` | 删除对话 |
| `PATCH` | `/api/v1/conversations/{id}` | 更新对话（标题/状态） |

---

### 5.2 P1: 执行控制（Phase 2）

#### F-101: Run 硬控制

新增 `RunCommand` 机制，允许 Operator 对正在执行的 Run 下发强制命令：

| 命令 | 效果 |
|------|------|
| `hard_abort` | 立即终止 Run，丢弃所有未完成的工作 |
| `soft_abort` | 等待当前工具调用完成后再终止 |
| `pause` | 暂停执行，等待继续指令 |
| `skip_tool` | 跳过当前正在执行的工具 |

**交互流程**：
1. 前端 Operator 面板发送命令
2. 后端写入 `RunCommand` 事件
3. Scheduler 每次循环开始前检查待处理命令
4. 执行对应操作并写入 `CommandExecuted` 事件

#### F-102: 异常自动熔断

Monitor 在检测到以下情况时自动触发硬控制：

| 熔断条件 | 阈值 | 动作 |
|----------|------|------|
| 连续工具调用失败 | ≥3 次 | 暂停 Run，通知 Operator |
| 确认请求卡死 | ≥3 次未确认 | 自动拒绝确认并继续 |
| Token 消耗超限 | ≥预算 120% | Soft abort |
| 执行时间超限 | ≥配置的最大 duration | Hard abort |

---

### 5.3 P2: 串行 Fallback 路径优化（Phase 2）

#### F-201: Fallback Kernel 使用 tools API

当前 `_FallbackKernel` 使用文本指令格式（TOOL:/ARGS: 正则解析），改为使用 OpenAI tools API：

| 当前 | 目标 |
|------|------|
| 纯文本指令: `THOUGHT:... TOOL:... ARGS:...` | 结构化 tool_calls |
| 正则解析 LLM 输出 | 直接读取 `response.tool_calls` |
| 解析脆弱，工具输出含 JSON 时错位 | 原生 JSON Schema 支持 |
| 无 tools API 参数校验 | Schema 自动校验 |

---

### 5.4 P3: 上下文管理优化（Phase 3）

#### F-301: 动态上下文窗口

将硬编码 `window = 5` 改为基于 token 估算的动态窗口：

```
max_context_tokens = 8000  # 为对话上下文保留的空间
window = compute_dynamic_window(state, max_context_tokens)
# 在 token 预算内，尽量保留更多上下文轮次
```

**行为规则**：
- 优先保留最近 N 轮完整 thought + tool result
- 超出 token 预算时，从最旧的轮次开始逐步截断工具结果
- 极端压缩时只保留 thought 摘要

#### F-302: 工具结果智能截断

| 工具类型 | 截断策略 |
|----------|---------|
| `http_request` | body 保留前 2000 chars + status code |
| `browser` | 文本内容保留前 1000 chars |
| `file_op` | 内容保留前 500 chars |
| `search` | 结果保留前 3 条 |
| 其他 | 默认保留前 1000 chars |

### 5.5 P4: 前端优化（Phase 4）

#### F-401: 对话式 UI

```
当前 (ChatDrawer):
  ┌─────────────────┐
  │ Run abc12345     │ ← 仅显示一个 Run
  │ [用户消息]       │
  │ [Agent 回答]     │
  ├─────────────────┤
  │ [输入框] [Send]  │
  └─────────────────┘

目标 (ConversationDrawer):
  ┌──────────────────────────────────┐
  │ 对话标题: "帮我分析 XX"    [+]  │
  ├──────────────────────────────────┤
  │ 👤 帮我查天气                    │
  │ 🤖 东京今天 25°C，晴            │
  │                                  │
  │ 👤 用中文总结                    │ ← 引用上一轮上下文
  │ 🤖 东京天气：25°C，晴天...      │
  │                                  │
  │ 👤 那明天呢？                    │
  │ 🤖 (查询中...)                   │
  ├──────────────────────────────────┤
  │ [输入框]                   [Send]│
  └──────────────────────────────────┘
```

#### F-402: 对话侧边栏

| 功能 | 说明 |
|------|------|
| 对话列表 | 按更新时间排序，显示标题/摘要/时间 |
| 搜索 | 按对话标题/内容搜索 |
| 新建对话 | 点击"+"创建空白对话 |
| 删除对话 | 右键菜单删除 |
| 展开/折叠 | 侧边栏可折叠为图标 |

#### F-403: 排队输入

用户在 Run 运行时可以输入下一条消息，系统自动排队：

1. 用户输入下一条消息
2. 消息显示为"待处理"状态
3. 当前 Run 完成后自动执行下一条
4. 用户可取消排队中的消息

#### F-404: Agent 思考可视化

| 元素 | 交互 |
|------|------|
| 思考链 | 可折叠/展开，默认折叠 |
| 工具调用 | 实时状态卡片（搜索中.../已完成 ✅） |
| 确认请求 | 按钮式确认/拒绝，显示 risk_level |
| 最终回答 | Markdown 渲染 |

### 5.6 P5: 持久化对话记忆（Phase 5）

#### F-501: 对话级向量记忆

| 能力 | 说明 |
|------|------|
| 关键事实提取 | 每轮对话自动提取关键事实存入记忆 |
| 工具结果缓存 | 避免重复查询相同信息 |
| 用户偏好学习 | 格式偏好、详细程度、语言偏好 |
| 跨对话引用 | 用户可引用"我上次让你做的那个分析" |

**记忆结构**：
```python
class ConversationMemory:
    conversation_id: str
    key_facts: list[str]       # "用户偏好日语回复"
    tool_results_cache: dict   # "东京天气已查过→25°C"
    preferences: dict          # "用户喜欢简短回答"
```

## 7. 验收标准

### 7.1 Phase 1 验收标准

| 标准 | 验证方式 |
|------|---------|
| 用户可创建新对话 | POST /api/v1/conversations → 201 |
| 对话中发送消息触发 Run 执行 | POST /api/v1/conversations/{id}/messages → RunStarted 事件 |
| 第 N+1 轮能引用第 N 轮上下文 | System Prompt 包含前一轮摘要 |
| 对话列表可查看历史对话 | GET /api/v1/conversations → 列表 |
| 刷新页面后对话不丢失 | F5 → 同一对话可继续聊天 |
| 存量 Run 兼容 | 现有 Run 列表接口不变 |

### 7.2 Phase 2 验收标准

| 标准 | 验证方式 |
|------|---------|
| Operator 可强制终止 Run | 下发 hard_abort → Run 停止执行 |
| Operator 可暂停/恢复 Run | 下发 pause → 暂停；下发 resume → 继续 |
| 连续 3 次工具失败自动暂停 | Monitor 自动触发 pause |
| Fallback 路径使用 tools API | FallbackKernel 返回 tool_calls |

### 7.3 Phase 3 验收标准

| 标准 | 验证方式 |
|------|---------|
| 简单任务保留 >5 轮上下文 | token 估算后窗口 >5 |
| LLM 超大结果被截断 | 工具结果按策略截断 |
| 上下文压缩后信息不丢失 | 压缩后关键 facts 保留 |

### 7.4 Phase 4 验收标准

| 标准 | 验证方式 |
|------|---------|
| 用户可在 Run 运行时输入下一条消息 | 输入框不 disabled |
| 排队消息自动执行 | 当前 Run 完成后立即开始下一条 |
| 对话侧边栏显示历史对话列表 | 列表排序正确，可搜索 |
| Agent 思考可折叠 | 点击折叠动画流畅 |

## 8. 版本路线图

### 8.1 版本规划

| 版本 | 阶段 | 核心交付 | 时间估算 |
|------|------|----------|---------|
| v1.1 | Phase 1 | 最小可行多轮对话（后端） | 2 周 |
| v1.2 | Phase 2 | 执行控制 + Fallback 优化 | 2 周 |
| v1.3 | Phase 3 | 上下文管理优化 | 1 周 |
| v1.4 | Phase 4 | 对话式前端 UI | 3 周 |
| v2.0 | Phase 5 | 持久化对话记忆 | 2 周 |

### 8.2 发布策略

```
v1.1 ─→ v1.2 ─→ v1.3 ─→ v1.4 ─→ v2.0
                            ↑
                    用户可感知的完整体验
                    (此时才面向真实用户推广)
```

**原因**：v1.1 是多轮对话的基石，但后端改造在前端无感知。直到 v1.4 前端完成重写后，用户才能体验到完整的对话式交互。在此之前保持内部测试。

## 9. 依赖与风险

### 9.1 依赖

| 依赖 | 说明 |
|------|------|
| Event Store 需支持多维度查询 | 当前只有 `run_id` 索引，需新增 `conversation_id` 索引 |
| System Prompt 需新增对话级 Phase | 需确保不破坏现有 Prompt 结构 |
| 前端需重构 ChatDrawer | 当前 ChatDrawer 与 Run 1:1 绑定 |

### 9.2 风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 对话上下文注入过多导致 token 超限 | 中 | 高 | 动态窗口 + 智能截断 |
| 现有后端改动影响 Planner-Executor 路径 | 中 | 中 | 新增接口，不改动现有路径 |
| 前端重构周期长 | 高 | 中 | 分步交付：先改后端 API，再迭代前端 |
| 持久化记忆增加架构复杂度 | 低 | 高 | Phase 5 前做充分的技术验证 |

## 10. 术语表

| 术语 | 定义 |
|------|------|
| **Conversation** | 多轮对话线程，包含 1~N 个 Run |
| **Run** | 单次任务执行单元，由用户一条消息触发 |
| **Message** | 对话中的单条消息（用户消息或 Agent 回复） |
| **Session** | 用户与系统的交互会话，可包含多个 Conversation |
| **RunCommand** | Operator 对 Run 的强制控制指令 |
| **Guardrail** | 安全校验规则，强制拦截危险操作 |
