# PRD: Harness UI 重构 — 以对话为中心的简洁界面

> **版本**: v1.0
> **状态**: Draft
> **产品经理**: AgentX
> **日期**: 2026-07-22
> **来源**: 用户反馈 + 现有前端代码审计

---

## 1. 执行摘要

当前 Harness 前端有 **8 个页面、6 个导航入口**，大量信息重复展示在不同页面中。用户的核心诉求是：**在聊天界面中实时看到 Agent 在做什么，发现误解能立即暂停修正，想看详情时点一下就能一目了然。**

本 PRD 提出将 8 个页面整合为 **3 个核心视图**，以对话聊天为绝对中心，将监控、分析、配置等信息按需嵌入，消除页面跳转和信息重复。

---

## 2. 问题分析

### 2.1 现有页面信息重叠矩阵

| 信息维度 | Dashboard | Tools | Guardrails | Runs | Ops Dashboard | Ops System | RunAnalysis | RunDetail |
|----------|-----------|-------|------------|------|---------------|------------|-------------|-----------|
| Run 状态统计 | ✅ KPI 卡片 | | | ✅ 列表 | ✅ KPI 卡片 + 列表 | | ✅ 详情 | ✅ 详情 |
| Tool 调用统计 | ✅ Quick Nav | ✅ 完整表格 | | | ✅ 图表 + 表格 | ✅ 数量 | ✅  traces | ✅ 事件流 |
| Guardrail 触发 | ✅ Quick Nav | | ✅ 完整表格 | | ✅ 完整表格 | | ✅ 计数 | ✅ 事件流 |
| Run 事件流 | | | | | | | ✅ 时间线 | ✅ 原始流 |
| Scheduler 状态 | | | | | ✅ 表格 | | | |
| MCP Server | | | | | ✅ 状态面板 | | | |
| 系统配置 | | | | | | ✅ 完整 | | |
| 聊天/对话 | ✅ ChatDrawer | | | | ✅ ConversationView | | ✅ ChatDrawer | |

**结论**: 同一数据至少出现在 2~4 个页面中。用户需要在多个页面间跳转才能获取完整信息。

### 2.2 用户痛点

| 痛点 | 当前行为 | 用户期望 |
|------|---------|---------|
| 信息分散 | 看 Run 状态要去 Runs 页，看工具统计要去 Tools 页，看 Guardrail 要去 Guardrails 页 | 在一个地方看到所有相关信息 |
| 聊天与监控分离 | OpsChatView 有聊天 + 实时监控，但 Dashboard 的 ChatDrawer 只有简单事件流 | 聊天时就能看到 Agent 每一步在做什么 |
| 无法中途干预 | 暂停/恢复按钮在 RunDetail 页，聊天时输入框被禁用 | 聊天界面内直接暂停，修正后继续 |
| 详情获取成本高 | 要看完整执行流程需要跳转到 RunAnalysis 或 RunDetail | 点击对话中的某一步就能展开详情 |
| 导航复杂 | 6 个导航入口，两个平行导航体系（/analysis 和 /ops） | 清晰的导航，一眼知道在哪 |

### 2.3 根因

1. **演进式开发导致页面堆砌**: 每个功能模块独立开发页面，缺乏整体 UI 规划
2. **两套平行导航**: `/analysis/*`（分析视角）和 `/ops/*`（运维视角）本质服务同一用户
3. **聊天不是第一公民**: ChatDrawer 是嵌入在其他页面中的侧边栏，而非主界面
4. **信息架构按技术组件划分**: 页面按后端组件（Tools、Guardrails、Scheduler）组织，而非按用户任务组织

## 3. 用户角色

| 角色 | 描述 | 核心场景 |
|------|------|---------|
| **日常用户** | 通过聊天与 Agent 交互，完成任务 | 发消息 → 看 Agent 执行 → 发现问题暂停 → 查看详情 → 继续对话 |
| **运维人员** | 监控 Agent 系统健康度，排查问题 | 查看系统状态 → 定位异常 Run → 查看执行详情 → 干预 |

**本版本聚焦日常用户场景**，运维能力作为二级入口保留。

---

## 4. 产品目标

### 4.1 目标

1. **聊天即主界面**: 打开应用直接进入聊天界面，而非 Dashboard 或 Run 列表
2. **实时可见**: 聊天界面内实时展示 Agent 的思考、工具调用、执行结果
3. **一键干预**: 聊天界面内直接暂停/恢复，无需跳转页面
4. **按需详情**: 点击对话中的任意步骤，展开查看完整执行详情
5. **页面精简**: 从 8 个页面减少到 3 个核心视图

### 4.2 非目标

- 不改变后端 API 和数据模型
- 不改变事件溯源架构
- 不实现新的 Agent 能力
- 本版本不实现多用户协作

## 5. 功能需求

### 5.1 P0: 页面整合（Phase 1）

#### F-001: 聊天主界面

**描述**: 应用默认页面为聊天界面，左侧为对话列表，中间为聊天区域，右侧为实时执行面板。

**验收标准**:
- 打开应用直接进入聊天界面
- 左侧显示对话列表（支持搜索、新建、删除）
- 中间显示当前对话的消息流（用户消息 + Agent 回复）
- 右侧实时展示当前 Run 的执行状态（思考、工具调用、结果）
- Agent 执行时输入框可用，消息进入排队队列

#### F-002: 实时执行面板

**描述**: 聊天界面右侧面板，实时展示 Agent 当前 Run 的执行细节。

**验收标准**:
- 显示当前 Run 的状态（running/paused/completed/failed）
- 实时展示 AgentThought（思考内容，可折叠）
- 实时展示 ToolCalled/ToolCompleted/ToolFailed（工具调用卡片）
- 展示 GuardrailTriggered 事件（警告样式）
- 展示 ConfirmationRequested（确认卡片，可直接 Approve/Deny）
- WebSocket 断开时显示重连状态

#### F-003: 聊天内暂停/恢复

**描述**: 用户在聊天界面内可直接暂停正在执行的 Run。

**验收标准**:
- Run 执行中时，聊天输入框旁显示"暂停"按钮
- 点击暂停后，Run 状态变为 paused，输入框恢复可用
- 用户可输入新消息或点击"恢复"继续当前 Run
- 暂停/恢复操作在聊天界面内完成，无需跳转

#### F-004: 步骤详情展开

**描述**: 用户点击实时执行面板中的任意步骤，展开查看完整详情。

**验收标准**:
- 点击 ToolCalled 卡片 → 展开显示完整 input/output JSON
- 点击 AgentThought → 展开显示完整思考内容
- 点击 GuardrailTriggered → 展开显示完整拦截原因
- 展开区域支持折叠回去
- 详情展示不影响聊天输入和实时事件流

### 5.2 P1: 二级页面（Phase 2）

#### F-005: 系统概览页

**描述**: 整合原 Dashboard + Ops Dashboard 的系统级统计信息。

**验收标准**:
- 显示 Run 状态统计（总数、运行中、完成、失败）
- 显示 Tool 调用统计（总调用数、成功率）
- 显示 Guardrail 触发统计
- 显示 MCP Server 连接状态
- 显示 Scheduler 活跃状态
- 提供跳转到聊天界面的入口

#### F-006: Run 历史页

**描述**: 整合原 RunList + RunAnalysis 的 Run 历史查看功能。

**验收标准**:
- 显示所有 Run 的列表（支持按状态过滤）
- 点击 Run → 显示完整事件时间线
- 显示 Tool Trace 树状图
- 提供 KPI 统计（事件数、工具调用数、Token 消耗、耗时）

### 5.3 P2: 体验优化（Phase 3）

#### F-007: 对话级执行摘要

**描述**: 在对话列表中显示每个对话的执行摘要。

**验收标准**:
- 对话列表项显示最近一条消息摘要
- 显示对话内 Run 的执行状态（成功/失败/进行中）
- 显示对话的消息数量和最后更新时间

#### F-008: 全局搜索

**描述**: 支持跨对话、跨 Run 的全局搜索。

**验收标准**:
- 搜索框支持按关键词搜索对话标题、消息内容、Run intent
- 搜索结果按相关性排序
- 点击搜索结果跳转到对应对话

## 6. 信息架构

### 6.1 新导航结构

```
Harness
├── Chat (默认页)          ← 原 OpsChatView + Dashboard.ChatDrawer 整合
│   ├── 对话列表 (左侧栏)
│   ├── 聊天区域 (中间)
│   └── 实时执行面板 (右侧)
── Overview               ← 原 Dashboard + OpsDashboard 整合
│   ├── 系统 KPI
│   ├── Tool 统计
│   ├── Guardrail 统计
│   └── MCP Server 状态
└── History                ← 原 RunList + RunAnalysis 整合
    ├── Run 列表
    └── Run 详情 (时间线 + Trace)
```

### 6.2 页面映射关系

| 新页面 | 继承自 | 移除的重复信息 |
|--------|--------|---------------|
| Chat | OpsChatView + Dashboard.ChatDrawer | Dashboard 的 KPI 卡片（移到 Overview） |
| Overview | Dashboard + OpsDashboard | 聊天功能（移到 Chat） |
| History | RunList + RunAnalysis + RunDetail | 单独的 RunDetail 路由（合并到 History 内） |

**删除的页面**: ToolsPanel、GuardrailPanel、OpsSystem、RunDetail（独立路由）

**保留为二级入口的信息**:
- Tool 统计 → Overview 页的 Tool 区域
- Guardrail 统计 → Overview 页的 Guardrail 区域
- 系统配置 → Overview 页的系统信息区域（简化展示）

## 7. 非功能需求

### 7.1 性能

- 聊天界面首屏加载 < 1s
- WebSocket 事件渲染延迟 < 200ms
- 对话列表加载 < 500ms

### 7.2 兼容性

- 保持所有现有后端 API 不变
- 保持 WebSocket 协议不变
- 前端路由变更需做好旧路由重定向

### 7.3 可访问性

- 所有交互元素支持键盘操作
- 颜色对比度符合 WCAG 2.1 AA 标准
- 实时面板支持屏幕阅读器

## 9. 成功指标

| 指标 | 当前基线 | 目标值 |
|------|---------|--------|
| 用户完成任务的平均页面跳转次数 | 3~4 次 | ≤ 1 次 |
| 从发现问题到暂停 Agent 的操作步数 | 3 步（跳转 RunDetail → 找按钮 → 点击） | 1 步（聊天界面内点击） |
| 查看 Run 详情的操作步数 | 2 步（跳转 RunAnalysis/RunDetail） | 1 步（点击步骤展开） |
| 前端页面数量 | 8 个 | 3 个 |
| 导航入口数量 | 6 个 | 3 个 |
