## 0. 修订记录（v2.1 修正，2026-08-04）

**Bug S1.1**：v2.0 实现中 `should_not_rerun` 在纯 `ExecState` 判定之外额外读取了 `task_state`
（`... and self.task_state != NOT_ACHIEVED`），使系统强制依赖 LLM 配合（约束 4 被违反）。
本次修订：

- `should_not_rerun` **不含 SOFT_ERROR**（SOFT_ERROR 可重跑），且**不读取 `task_state`**；
- `is_done` 与 `should_not_rerun` **解耦**，`is_done` 含 SOFT_ERROR（管层失败判定/上游上下文/完成计数）；
- `task_state` 降级为**纯注解**（仅展示给 LLM，不进入任何受信判定）；
- SOFT_ERROR 结果**不入幂等缓存**（同输入重跑须真实再执行）；
- COMPLETED 步骤重做须**新建 step id**（系统静默跳过已完成 id）。

详细设计见 `TDD_S1_任务完成语义分层.md` §0 与 `ARCHITECTURE_v2.1.md` §3.7.6。

### 0.2 v2.2 修订（完成门 + step_normal + probe + 可溯源，2026-08-07）

> 来源：`Handover/completion_semantics_chain_redesign_handover_20260807.md` 决策 D1–D11。
> 目标：U1（自愈不收敛）/ U2（完成脱钩）根治，修复审计 P0-03。

**概念反转**：v1.x 的"完成的判定权归 Agent"（§1.2 原则 3）在 v2.2 起**失效**。
任务完成改为**系统机械聚合**（D5）——最终计划所有步骤 `step_normal` 的聚合，
不再信任 LLM 的"空 steps"一句话。

| 决策 | 内容 |
|---|---|
| D1 | 改名 `ExecState.SOFT_ERROR` → `UNSUCCESSFUL`（"错误的一种"误导；实为"跑了但没拿到东西"）。同步 `ToolResultType.SOFT_ERROR`、`has_soft_error`→`is_unsuccessful`、前端/分析 API `"soft_error"→"unsuccessful"` |
| D2 | AND 语义：工具跑完 **且** 拿到东西才算干成。UNSUCCESSFUL = 默认不算正常 |
| D3 | `step_normal = exec_state ∈ {COMPLETED, IDEMPOTENT}` 或 `(exec_state == UNSUCCESSFUL and step.probe)`。纯系统计算，不读 task_state（约束 4） |
| D4 | `step.probe = true` 仅允许无副作用（只读/查询）工具步骤可标 |
| D5 | 任务完成 = 最终计划所有步骤 `step_normal` 的聚合 |
| D6 | 可溯源：`step_id ↔ tool_call_id` 挂钩 + 计划结构落事件 |
| D7 | probe 否定答案不阻断下游。门控条件**唯一** = `step_normal`；系统不猜下游能否消费否定答案 |
| D8 | `is_done` 收窄为 `output_available`（输出可用，仅 planner 的 `available_step_ids` 用）；完成计数/上游注入/layer 检查改用 `step_normal` |
| D9 | SKIPPED 算未达成，暂不做 waive；门控产生 SKIPPED 需补记录（现全库无生产者、不落事件） |
| D10 | probe 信任校验放 **PlanGuardrail**（受信）：`if step.probe and tool_def.side_effects → reject` |
| D11 | `task_state` 保留为**纯审计便签**：落事件供审计；未来延申为"LLM 自评 vs 系统机械判定"差异对比展示。**仍不参与任何受信判定（约束 4）**。注释见 `ARCHITECTURE_v2.1.md` §3.7 |

**状态语义最终表**：

```
COMPLETED    = 工具跑完 + 拿到东西         → 步骤正常 ✓
IDEMPOTENT   = 幂等命中（等效拿到）         → 步骤正常 ✓
UNSUCCESSFUL = 工具跑完 + 没拿到东西       → 默认不正常 ✗；probe=true 时算正常 ✓
FAILED       = 工具没跑成（崩溃/超时/拦截） → 步骤不正常 ✗
SKIPPED      = 被跳过（因依赖不正常）       → 步骤不正常 ✗
```

**下游门控（P0-03 修复）**：依赖步骤非 normal → 下游 SKIP 不执行，等 revise 修复。
fail-safe：宁可标"未达成"，绝不假绿。

## 1. 背景与问题陈述

V0.7 在 `harness/core/dag_types.py:13-18` 引入了五元 `StepStatus` 枚举：

```
COMPLETED  SOFT_ERROR  FAILED  CONFIRMATION_NEEDED  EXECUTOR_ERROR
```

**核心问题**："工具完成状态"与"任务完成语义"被混为一谈，产生系统性歧义。

### 1.1 具体症状

| 症状 | 位置 | 影响 |
|---|---|---|
| `"idempotency_hit"` 是死代码 | `planner.py:276` | 全项目无写入路径，误导维护者 |
| `SOFT_ERROR` 未被计入"不应重排" | `planner.py:274-276` | 但 `StepResult.is_done=True`，语义自相矛盾 |
| dict-compat `.get("status")` 依赖 backward-compat | `dag_types.py:37-51` | 薄冰层，随时可能断裂 |
| **核心歧义** | 全局 | "step 不应重排"的判据是 **工具执行态** 还是 **任务达成态**？两者不等价 |

### 1.2 违反的设计原则

当前实现违反了以下已确立原则：

1. **工具成功 ≠ 任务完成**：HTTP 200 不代表业务目标达成
2. **工具失败 ≠ 任务失败**：可重试的工具瞬时失败不应触发重排
3. ~~**完成的判定权归 Agent，执行态归系统**~~ → **v2.2 失效（见 §0.2 D5）**：任务完成改为**系统机械聚合** `step_normal`，不再由 LLM 一句话判定。系统只读 `exec_state`（系统写）+ `step.probe`（受信校验后的声明），不读 `task_state`
4. 不在受信组件层用启发式规则推导任务完成 —— v2.2 起**完成判定为机械聚合而非启发式**，聚合规则 `step_normal` 全分支由受信组件强制

---

## 2. 决策

### 2.1 核心决策

> **将 "工具执行态" 与 "任务达成态" 拆分为两个正交枚举，中间用显式 `should_not_rerun` 属性桥接。**

### 2.2 业界依据

| 项目 | 分层模式 | 对应本方案 |
|---|---|---|
| **Airflow** | `TaskInstanceState` (执行态) vs `DagRunState` (任务态) | `ExecState` vs `TaskState` |
| **Temporal** | `ActivityResult` (工具层) vs `Workflow` 决策 (任务层) | `StepResult.output` vs LLM revise |
| **LangGraph** | `end_node` 显式终止条件 | LLM 返回 `steps=[]` 判定完成 |
| **AutoGen** | `termination_condition` 由 orchestrator 判定 | LLM 在 revise 中判定 `task_state` |

## 3. 详细设计

### 3.1 数据模型

```python
# dag_types.py

from enum import Enum
from dataclasses import dataclass, field
from typing import Any, Optional


# 维度 1: 工具执行态 (ExecState)
# 由 DagExecutor 根据工具返回值判定
# 回答: "这个 step 的工具调用现在处于什么执行阶段？"
class ExecState(str, Enum):
    PENDING       = "pending"        # 尚未执行
    RUNNING       = "running"        # 正在执行
    COMPLETED     = "completed"      # 工具正常返回 (HTTP 200, 文件写入成功等)
    UNSUCCESSFUL  = "unsuccessful"   # 工具返回了, 但没拿到东西 (v2.2 由 SOFT_ERROR 改名)
    FAILED        = "failed"         # 工具执行失败 (HTTP 500, 超时, 异常)
    SKIPPED       = "skipped"        # 因上游失败/条件不满足被跳过
    IDEMPOTENT    = "idempotent"     # 幂等命中, 工具未真实执行
    CANCELLED     = "cancelled"      # 被外部取消


# 维度 2: 任务达成态 (TaskState)
# 由 Planner (LLM) 在 revise() 中判定
# 回答: "这个 step 的业务目标达成了吗？"
class TaskState(str, Enum):
    UNKNOWN       = "unknown"        # 尚未判定 (初始状态)
    ACHIEVED      = "achieved"       # LLM 判定目标已达成
    PARTIAL       = "partial"        # LLM 判定部分达成, 可能需要补充
    NOT_ACHIEVED  = "not_achieved"   # LLM 判定目标未达成, 需重试或重排
    WAIVED        = "waived"         # LLM 判定此目标可放弃


# StepResult: 承载两个维度的完整结果
@dataclass
class StepResult:
    # 设计原则:
    #   - exec_state 由系统写, Planner 只读 (告知"发生了什么")
    #   - task_state 由 LLM 在 revise 中写 (决策"目标是否达成")
    #   - should_not_rerun 由系统根据 exec_state 推导, Planner 只读

    step_id: str
    exec_state: ExecState

    # 执行态原始输出
    output: Any = None
    error: Optional[str] = None

    # 任务达成态 (由 LLM 在 revise 中填充)
    task_state: TaskState = field(default=TaskState.UNKNOWN)

    # v2.2: 探测型步骤声明 (仅无副作用工具步骤可标, PlanGuardrail 强制)
    probe: bool = field(default=False)

    # 关键属性: 显式标记"这个 step 不应被重跑"
    @property
    def should_not_rerun(self) -> bool:
        # 返回 True 表示这个 step 的工具已经执行过, 不应再次调度。
        # 注意: 这不等于"任务目标已达成", 只是"工具已经跑过了"。
        # v2.1 修正: 纯 ExecState 状态机, 不读取 task_state (受信边界约束 4)。
        # v2.2: UNSUCCESSFUL (原 SOFT_ERROR) 仍不在其中 → 可重跑。
        # 包含状态:
        #   - COMPLETED: 正常执行完毕
        #   - IDEMPOTENT: 命中缓存, 等效于已执行
        #   - SKIPPED: 被跳过, 等效于已处理
        #   - CANCELLED: 被取消, 不再执行
        return self.exec_state in (
            ExecState.COMPLETED,
            ExecState.IDEMPOTENT,
            ExecState.SKIPPED,
            ExecState.CANCELLED,
        )

    # v2.2 新增: 步骤是否"正常" (完成门的原子判据)
    # 纯函数 (exec_state, probe) → bool, 系统计算, 不读 task_state (约束 4)。
    # probe 需要 planner 传入该 step 的声明 (PlanGuardrail 已校验其仅无副作用工具可标)。
    @property
    def step_normal(self) -> bool:
        return self.exec_state in (
            ExecState.COMPLETED,
            ExecState.IDEMPOTENT,
        ) or (self.exec_state == ExecState.UNSUCCESSFUL and self.probe)

    # 向后兼容: 旧代码 .get("status") 继续工作
    def get(self, key: str, default=None):
        # Backward-compat shim. 将在迁移 Step 3 中移除.
        if key == "status":
            return self.exec_state.value
        return default
```

### 3.2 Planner.revise() 改造

```python
# planner.py

def revise(self, plan: Plan, results: dict[str, StepResult]) -> RevisedPlan:
    # 改造要点:
    #   1. completed_step_ids -> executed_step_ids (语义明确化)
    #   2. 给 LLM 的上下文包含 exec_state + task_state + output
    #   3. LLM 返回 steps=[] 表示判定整体任务完成
    #   4. 系统不推导任务完成, 只过滤"已执行且不应重跑"的 step

    # 1. 系统层: 哪些 step 已经执行过 (不应重跑)
    executed_step_ids = {
        sid for sid, r in results.items()
        if r.should_not_rerun  # 只问"执行过吗", 不问"达成了吗"
    }

    # 2. 构建给 LLM 的完整上下文
    context = self._build_revise_context(results)
    # context 结构示例:
    # {
    #   "step_1": {
    #     "exec_state": "completed",
    #     "task_state": "achieved",
    #     "output": {...},
    #     "should_not_rerun": True
    #   },
    #   "step_2": {
    #     "exec_state": "soft_error",
    #     "task_state": "partial",
    #     "output": {...},
    #     "error": "...",
    #     "should_not_rerun": True
    #   },
    #   "step_3": {
    #     "exec_state": "failed",
    #     "task_state": "not_achieved",
    #     "error": "timeout after 30s",
    #     "should_not_rerun": False
    #   }
    # }

    # 3. LLM 决策: 返回新的 steps (空列表 = 任务完成)
    revised = self.llm.revise(plan=plan, context=context)

    if not revised.steps:
        # LLM 判定整体任务完成
        return RevisedPlan(steps=[], task_complete=True)

    # 4. 过滤已执行的 step (LLM 可显式要求重跑)
    new_steps = [
        s for s in revised.steps
        if s.id not in executed_step_ids or s.force_rerun
    ]

    return RevisedPlan(steps=new_steps, task_complete=False)
```

### 3.3 PlanGuardrail / DagExecutor 依赖检查

```python
# dag_executor.py / plan_guardrail.py

def collect_upstream_results(
    self, 
    step: Step, 
    results: dict[str, StepResult]
) -> list[StepResult]:
    # 依赖检查只关心"上游是否已执行过", 不关心"上游任务是否达成"。
    # 如果上游 FAILED 但 should_not_rerun=True (即已经跑过了), 依赖检查通过。
    # LLM 在 revise 中可能决定重试或改方案, 那是 Agent 层的决策。

    upstream_results = []
    for dep_id in step.depends_on:
        if dep_id not in results:
            raise DependencyNotReady(dep_id)

        dep_result = results[dep_id]

        # 关键: 只检查"是否已执行", 不检查"是否成功"
        # FAILED 的 step 也是"已执行"的, 下游可以基于失败结果做决策
        if not dep_result.should_not_rerun:
            raise DependencyNotReady(dep_id)

        upstream_results.append(dep_result)

    return upstream_results
```

## 4. 状态映射对照表

### 4.1 旧 StepStatus -> 新 ExecState 映射

| 旧 `StepStatus` | 新 `ExecState` | 说明 |
|---|---|---|
| `COMPLETED` | `COMPLETED` | 直接映射 |
| `SOFT_ERROR` | `UNSUCCESSFUL` | 改名 (v2.2, D1): "跑了但没拿到东西" |
| `FAILED` | `FAILED` | 直接映射 |
| `CONFIRMATION_NEEDED` | `PENDING` + 附加 `confirmation_required=True` | 语义澄清: 等待用户确认 = 尚未执行 |
| `EXECUTOR_ERROR` | `FAILED` + `error` 字段标记来源 | 统一为 FAILED, 通过 error 区分来源 |
| *(死代码)* `"idempotency_hit"` | `IDEMPOTENT` | 正式枚举值替代字面量 |

### 4.2 ExecState -> should_not_rerun / step_normal 判定

| ExecState | should_not_rerun | step_normal (v2.2) | 理由 |
|---|---|---|---|
| `PENDING` | False | False | 尚未执行 |
| `RUNNING` | False | False | 正在执行 |
| `COMPLETED` | True | True | 正常执行完毕 |
| `UNSUCCESSFUL` | False (v2.1 起) | `probe` 时为 True, 否则 False | 跑了但没拿到; probe 声明后"没有"即正确答案 |
| `FAILED` | False | False | 执行失败, 可能需重试 |
| `SKIPPED` | False (v2.2 D9) | False | 被跳过 (因依赖非 normal), 工具未执行，修复依赖后可重跑 |
| `IDEMPOTENT` | True | True | 命中缓存, 等效于已执行 |
| `CANCELLED` | True | False | 被取消, 不再执行 |

## 6. 待设计点决议

| 待设计点 | 决议 | 理由 |
|---|---|---|
| `completed_step_ids` 的语义 | 改名为 `executed_step_ids`, 语义 = "step 已执行且不重试" | 满足 `PlanGuardrail` 依赖检查; 任务达成由 LLM 判定 |
| `SOFT_ERROR` 是否计入 | 计入 `should_not_rerun=True`, 但 `task_state` 初始为 `UNKNOWN` | 工具已跑过不应重跑; 目标是否达成由 LLM 看 output 决定 |
| `IDEMPOTENCY_HIT` 处理 | 引入正式枚举值 `ExecState.IDEMPOTENT` | 替代死代码 `"idempotency_hit"`; 与 `COMPLETED` 区分 |
| 是否新增"任务达成度"维度 | 引入 `TaskState` 正交枚举 | 避免单枚举扛双重语义; 与 Airflow/Temporal 对齐 |
