## 1. 摘要

工具层缺乏统一"基础标准"：每个工具 = 一个手工书写的长 `ToolDefinition` + 一个 `fn`，散落在 `harness/tools/`，由 `serve.py` 手工拼两个 dict 注册；executor、guardrails、intent 中对**具体工具名**的硬编码特判散落 7+ 处。每新增一个工具，作者要维护 7 处以上的散点，且 per-operation 契约（`OperationContract`）存在大量重复 schema。

本 ADR 固化"**声明 + 实现 + 装配**"三件事分离的工具标准：工具作者只写一个 `BaseTool` 子类（声明契约）+ 业务方法，横切能力（schema 校验、guardrails、幂等、确认、事件、超时、重试、语义判定、LLM schema 暴露、依赖注入、生命周期、注册装配）由统一基座自动提供。**新增工具 = 新增一个类 + 一行注册**。

**信任边界不变**：`ToolExecutor` 仍是唯一受信执行入口，8 步链与全部横切能力留在受信侧；`BaseTool` 是"定义载体"（非受信），其产出经受信 `ToolRegistry` 接线。所有名称特判收敛进工具声明（契约驱动），受信组件只做行为等价重构。

## 2. 背景与问题

### 2.1 现状调用链

```text
Scheduler(plan.py/loop.py)
  → DagExecutor.execute_step
      → registry.get_tool_def(step.tool) + registry.get_tool_fn(step.tool)
      → ToolExecutor.execute(run_id, tool, input, tool_def, tool_fn,
                             step_id, workspace_scope, backend, workspace_id)
          → GuardrailRunner（schema/scope/destructive/depends_on）
          → IdempotencyKeyGenerator → Confirmation
          → ToolCalled 事件
          → Sandbox.invoke(tool_fn, input, timeout)     ← 唯一调用工具函数
          → RetryRunner → SemanticEvaluator
          → ToolCompleted / ToolFailed / ToolTimeout 事件
```

### 2.2 每加一个工具要维护的散点

| 位置 | 问题 | 具体例子 |
|---|---|---|
| `harness/tools/*.py` | 手工书写长 `ToolDefinition`，per-op `output_schema` 大量重复 | `file_op` 5 个 `OperationContract` 有 4 份几乎相同的 output_schema（约 120 行样板） |
| `api/serve.py:142`、`api/deps.py:63` | 手工维护 `tool_defs` + `tool_fns` 双列表 | 加工具要同时改两处 |
| `tools/executor.py:380` | 硬编码 `if tool_name == "file_op"` 注入 backend | 新工具需要 backend 须再加分支 |
| `models/tools.py:107` | 硬编码 `if tool_def.name == "http_request"` 猜默认 GET；判别键靠魔法 `_OPERATION_KEYS=("operation","method","action")` | 新判别键工具（如 `command`）须改魔法元组 |
| `tools/guardrails.py:82/119/253/261/269` | Scope / Destructive 按工具名特判 | `run_code` 分支在代码库中**没有注册**（死特判） |
| `models/intent.py:55-81` | `required_by_tool` 硬编码判别键表 + `if tool == "file_op"` content 校验 | 契约层耦合工具内部细节 |
| 生命周期 | browser / http client / mcp manager / backend 各自 close，无统一接口 | serve 关闭时无人统一回收 |
| `tools/mcp_manager.py:240` | `register(td, None)` → `dag_executor` 将 `fn=None` 拦截为 "Tool not registered"，MCP 动态工具无法直接执行 | 动态工具无标准注册路径 |
| `tools/skill.py` | `Skill` 手工 `build_fn` + 内部直接 `executor.execute(...)` | 脱离 registry 受信查找路径 |

### 2.3 根因

- **契约与实现分离度不足**：`ToolDefinition`（契约）与 `fn`（实现）是两个独立实体，无标准绑定方式。
- **契约表达力不足**：判别键、scope 目标、条件必填等语义没有结构化声明，只能用工具名特判表达。
- **横切能力无法按声明自动装配**：依赖注入、生命周期、注册没有统一入口。

## 3. 目标与原则

1. **信任边界不变**：`ToolExecutor` / `GuardrailRunner` / `IdempotencyKeyGenerator` / `RetryRunner` / `Sandbox` / `SemanticEvaluator` / `ToolRegistry` 为受信组件；`BaseTool`（定义）与工具业务方法为非受信组件。受信组件不因工具实现而退化。
2. **行为等价重构**：受信组件的特判收敛为契约驱动，对外可观察行为（事件序列、guardrail 判定、幂等、确认、完成语义）不变。由全量确定性测试守护。
3. **直接重构，不做历史兼容**：不保留旧 `register(td, fn)`、旧 fn 签名 `fn(input)`、旧双列表装配等既有接口；`register_tool` 为唯一注册路径，工具实现统一走 `run()` / `@operation` 方法。不处理历史数据/旧格式兼容。
4. **同源契约**：所有新增 Schema 用 Pydantic（AGENTS.md §4.1）；契约以 `ToolDefinition` / `OperationContract` 为唯一来源。
5. **显式注册**：工具通过 `registry.register_tool(ToolClass())` 显式注册（非自动扫描、非配置外部化），与现有架构风格一致。

## 4. 决策（D-01 ~ D-08）

> 全部已实施（2026-08-13，TDD+BDD 落地）。

| 编号 | 主题 | 冻结结论 |
|------|------|----------|
| D-01 | 声明式 `BaseTool` 抽象 | 新增 `harness/tools/base.py`：工具作者继承 `BaseTool`，用类属性声明契约，用 `@operation` 装饰器声明 per-operation 业务方法；`to_definition()` 自动合成 `ToolDefinition`（operation 未声明 output_schema 时继承工具级）。 |
| D-02 | 契约模型扩展 | `ToolDefinition` 增加 `operation_key`（默认 `"operation"`）、`default_operation`（默认 `None`）、`scope_targets: list[ToolScopeTarget]`；`OperationContract` 增加 `required_input: list[str]`。全部 Pydantic 同源、带默认值。 |
| D-03 | 统一注册与依赖注入 | `ToolRegistry.register_tool(tool)` 自动 `to_definition()` + 绑定 invoker + 装配依赖；run 级可变依赖（backend）经 contextvar（沿用 `current_run_id` 模式）由 executor 注入，executor 对所有工具统一 `Sandbox.invoke(tool_fn, input)`。 |
| D-04 | 受信组件契约化重构 | 删除 executor / guardrails / intent / `resolve_operation_contract` 中全部工具名特判，改为契约驱动（D-02 字段）。行为等价。 |
| D-05 | MCP 动态工具统一路径 | `mcp_manager` 动态工具构造 `BaseTool` 实例走 `register_tool`，invoker 永不 `None`——杜绝 `fn=None` 导致动态工具无法经 dag_executor 执行的问题。 |
| D-06 | Skill 纳入同一标准 | `Skill` 改为 `BaseTool` 子类（`run()` 编排子工具，子调用走受信 registry 路径），不再手工 `executor.execute` 拼接。 |
| D-07 | 显式列表注册 | `serve.py` / `deps.py` 用一行 `registry.register_tool(FileOpTool())` 等显式注册，删除双列表手工维护。 |
| D-08 | 生命周期统一 | `BaseTool.open()/close()` 可选；装配器启动时统一 `open()`、关闭时统一 `close()`，http client / BrowserManager / mcp manager / backend 资源回收收敛到各自 `close()`。 |

## 5. 目标架构

```text
工具作者写（非受信）：
┌─────────────────────────────────────────────────────────────┐
│ harness/tools/xxx.py                                        │
│ class XxxTool(BaseTool):                                    │
│     name = "xxx"; description = "..."                       │
│     input_schema = {...}; output_schema = {...}             │
│     operation_key = "action"; default_operation = "GET"     │
│     side_effects = [...]; idempotency_key_fields = [...]    │
│     guardrails = [Guardrail("scope", {})]                   │
│     scope_targets = [ToolScopeTarget("domain", "url")]      │
│     success_indicator = SuccessIndicator("ok","eq",True)    │
│     needs_backend = True                                    │
│     @operation("GET", side_effects=[], probe_allowed=True)  │
│     async def get(self, input) -> dict: ...                 │
│     async def close(self): ...                              │
└─────────────────────────────────────────────────────────────┘
        │  D-01 to_definition() + D-03 invoker/依赖注入
        ▼
受信侧：
ToolRegistry.register_tool(XxxTool())                          ← D-07 一行注册
        │  产出 ToolDefinition + invoker（依赖已装配）
        ▼
ToolExecutor 8 步链（schema/guardrails/幂等/确认/事件/超时/重试/语义）   ← 信任边界
        └─ Sandbox.invoke(invoker, input)                      ← executor 不再按名特判
```

### 5.1 分层职责

| 组件 | 信任属性 | 职责 | 不负责什么 |
|---|---|---|---|
| `BaseTool` 子类 | 非受信（定义） | 声明契约 + 实现业务 | 不执行 guardrails/幂等/事件 |
| `ToolRegistry` | 受信 | 接线、装配、invoker 绑定 | 不决定业务正确性 |
| `ToolExecutor` | 受信 | 8 步执行链、横切能力 | 不因工具实现退化 |
| `GuardrailRunner` 等 | 受信 | schema/scope/destructive/depends_on | 判定依据来自工具声明，非名称 |

## 6. 模型设计

### 6.1 `harness/tools/base.py`（新增）

```python
class ToolScopeTarget(BaseModel):
    """工具声明的 scope 目标（D-02），取代 ScopeGuardrail 名称特判。"""
    kind: Literal["path", "domain", "command"]
    input_field: str              # 从 input 提取目标的字段
    config_key: str = ""          # 白名单键；空则按 kind 默认（allowed_directories/domains/commands）

class BaseTool(ABC):
    # 声明（类属性，工具作者填写）
    name: ClassVar[str]
    description: ClassVar[str]
    input_schema: ClassVar[JSONSchema]
    output_schema: ClassVar[JSONSchema] = {}
    operation_key: ClassVar[str] = "operation"
    default_operation: ClassVar[str | None] = None
    side_effects: ClassVar[list[SideEffect]] = []
    idempotency_key_fields: ClassVar[list[str] | None] = None
    guardrails: ClassVar[list[Guardrail]] = []
    scope_targets: ClassVar[list[ToolScopeTarget]] = []
    requires_confirmation: ClassVar[bool] = False
    timeout_ms: ClassVar[int] = 30000
    retry_policy: ClassVar[RetryPolicy] = RetryPolicy()
    success_indicator: ClassVar[SuccessIndicator | None] = None
    dangerous_with: ClassVar[list[str]] = []
    max_parallel: ClassVar[int] = 10
    depends_on: ClassVar[list[DependencyConstraint]] = []
    needs_backend: ClassVar[bool] = False          # 依赖声明
    needs_mcp_manager: ClassVar[bool] = False

    # 生命周期（可选覆写）
    async def open(self) -> None: ...
    async def close(self) -> None: ...

    # 统一入口（基座自动合成）
    def to_definition(self) -> ToolDefinition: ...
    async def invoke(self, input, *, backend=None, run_id="") -> Any:
        """注入依赖 → 按 operation_key dispatch 到 @operation 方法 / run()"""

def operation(*, input_schema=None, output_schema=None, side_effects=None,
              requires_confirmation=None, idempotency_key_fields=None,
              probe_allowed=False, retry_policy=None, ref_allowed_fields=None) -> Callable:
    """标记业务方法并生成 OperationContract（D-01）。"""
```

要点：
- `@operation` 未声明 `output_schema` 时，`to_definition()` 让对应 `OperationContract` 继承工具级 `output_schema`（消灭重复样板）。
- `run()` 默认按 `input[operation_key]` 分发到 `@operation` 方法；无 operation 的工具直接覆写 `run()`。
- `needs_backend` / `needs_mcp_manager` 声明后，装配器把共享资源注入工具实例；`backend` 是 run 级可变依赖，由 executor 经 contextvar 注入（D-03）。

### 6.2 `harness/models/tools.py`（扩展字段，全部带默认值）

```python
class ToolDefinition(BaseModel):
    ...
    operation_key: str = "operation"                # D-02
    default_operation: str | None = None            # D-02
    scope_targets: list[ToolScopeTarget] = Field(default_factory=list)  # D-02

class OperationContract(BaseModel):
    ...
    required_input: list[str] = Field(default_factory=list)   # D-02
```

- `resolve_operation_contract` 改用 `tool_def.operation_key` 取判别值；无判别键且声明 `default_operation` 时返回该 operation（删除 `if name == "http_request"`）。
- `ToolScopeTarget` 定义于 `harness/tools/base.py` 或 `harness/models/tools.py`（推荐后者，保持契约模型集中于 models 层）。

## 7. 受信组件重构（D-04，行为等价）

### 7.1 `tools/executor.py`

- `execute()` 签名保留 `backend` 参数（dag_executor / scheduler 调用点零改动），仅内部注入方式变化。
- 删除 `:380` 的 `if tool_name == "file_op" and backend is not None: fn = partial(tool_fn, backend=backend)`。
- 调用前 `current_backend.set(backend)`（新增 contextvar，沿用 `current_run_id` 模式），统一 `Sandbox.invoke(tool_fn, input, timeout_ms=...)`。
- 所有工具函数统一经 invoker 调用（签名 `invoke(input, *, backend, run_id)`）；无 backend 声明的工具 invoker 忽略 ctx。

### 7.2 `tools/guardrails.py`

- **`ScopeGuardrail`**：遍历 `tool_def.scope_targets` 按 `kind` 通用判定：
  - `path`：有 backend → `backend.resolve(path)`；无 → 本地 `os.path` 判定（行为等价）。
  - `domain`：`urlparse` 提取 hostname，对照 `allowed_domains`。
  - `command`：`shlex.split` + 拒绝 shell 操作符，对照 `allowed_commands`。
  - 白名单键：`config.get(target.config_key)` 或按 kind 默认映射。
- **`DestructiveOpGuardrail`**：由契约驱动——命中的 `OperationContract.side_effects` 含 `DELETE` 或 `requires_confirmation=True` 时触发确认；`config.destructive_operations` 保留为覆盖项（file_op write 默认不触发，行为不变）。删除 `file_op` / `run_code` 名称特判。

### 7.3 `models/intent.py`

- 删除 `required_by_tool` 硬编码表与 `if tool == "file_op"` 特判。
- `validate_delivery_contract_input` 的必填键合成规则：
  `必填 = input_schema.required ∪ (仅当 tool_def.operations 非空时含 operation_key) ∪ 命中的 OperationContract.required_input`。
  - 判别键只对声明了 per-operation 契约的工具必填（mcp_call 无 operations，不要求判别键，避免误加 `operation`）；
  - `http_request` 因声明 operations，判别键 `method` 必填（即使 schema 有 default）——与现状"method+url 必填"行为等价；
  - `file_op` write/append 的 `required_input=["operation","path","content"]` 使 content 必填。
- 行为等价：file_op 需 operation+path、http_request 需 method+url、browser 需 action、mcp_call 需 tool_name、file_op write/append 需 content。

## 8. 注册、装配与实施

### 8.1 `tools/registry.py`

```python
class ToolRegistry:
    def register_tool(self, tool: BaseTool) -> str:
        td = tool.to_definition()
        invoker = make_invoker(tool)          # 捕获实例 + 从 ctx 读 backend
        self._tools[td.name] = td
        self._fns[td.name] = invoker
        return td.name
```

- `register_tool` 是唯一注册入口，`register(td, fn)` 旧接口不再保留。
- `get_tool_def` / `get_tool_fn` / `list_tool_defs` / `list_tool_fns` 保持为受信查询接口（dag_executor / scheduler / `build_llm_schemas` / skill 读取路径不变），对外只暴露 `BaseTool` 注册。
- `HarnessAPI.tool_defs` / `tool_fns` 字段保留（`BaseScheduler` 构造签名不变），由 `serve.py` 从 `registry.list_tool_defs()` / `list_tool_fns()` 派生，不再手工维护。

### 8.2 实施顺序（一次性重构，不分区段兼容）

1. 新增 `harness/tools/base.py`（BaseTool / @operation / ToolScopeTarget / invoker）+ `models/tools.py` 契约字段（`operation_key` / `default_operation` / `scope_targets` / `required_input`）。
2. `ToolRegistry` 改为 `register_tool` 唯一入口。
3. 受信组件契约化重构：executor / guardrails / intent / `resolve_operation_contract` 删除全部名称特判。
4. 4 个工具改写为 `BaseTool` 子类：file_op / http_request / browser / mcp_call；`serve.py` / `deps.py` 改显式一行注册（D-07）。

## 10. 风险

- **受信组件行为等价重构跑偏**：一次性重构后全量测试守护；`file_op` backend 注入路径专门测试。重构不保留旧接口/旧 fn，测试与装配点同步更新。
- **测试迁移量**：现有约 70 处 `registry.register(...)` 测试调用需同步改造——改用 `register_tool` + 最小 `BaseTool` 测试类，或经受信内部存储原语 `_register(td, fn)`（`register_tool` 的私有实现，非公开注册入口）。`_register` 仅为降低测试样板，不构成公开兼容接口。
- **`ToolScopeTarget` 归属**：推荐定义于 `models/tools.py`（契约模型集中）；若发现循环依赖则置于 `base.py` 并由 `models` 导入。
- **不做历史兼容的连带影响**：旧工具文件、旧注册调用点、依赖旧 `register(td, fn)` 的外部脚本需要同步改造；本方案明确放弃这些兼容负担，一次性迁移到位。

## 11. 记录在案的限制

- **L-01 path scope 判定**：有 backend 时走 `backend.resolve`，无 backend 时本地 `os.path` 判定；两条路径判定语义一致。
- **L-02 destructive 覆盖项**：`config.destructive_operations` 保留为覆盖项（file_op write 默认不触发确认），契约（DELETE/requires_confirmation）为默认判定依据。
- **L-03 工具发现**：显式列表注册（D-07）；不支持自动扫描与配置文件开闭，避免隐式魔法与配置校验成本。
- **L-04 可观测性特判**：`monitoring/run_monitor.py:445` 对 `http_request` 的 URL 提取特判属可观测性层（非受信执行链），不在本轮范围内；后续可由工具声明驱动，本轮不处理。
- **L-05 legacy 导出保留**：旧 `*_DEF` / `*_fn`（`FILE_OP_DEF`、`HTTP_REQUEST_DEF` 等）保留为只读兼容导出，供既有测试与脚本引用；注册入口已收敛为 `register_tool`（`register` 不复存在），新工具开发一律走 BaseTool。旧导出不影响"新增工具=一个类+一行注册"的标准。
