### P0-1: API Schema 重复定义 — 违反同源原则 (AGENTS.md §4.1)

**文件**: `harness/models/conversation.py:14-66` vs `harness/api/schemas.py:79-118`

`harness/api/schemas.py` 中定义了 7 个与 `harness/models/conversation.py` 字段高度重复的 Schema 类：

| API schemas.py | Domain models/conversation.py | 差异 |
|---|---|---|
| `ConversationResponse` | `Conversation` | 字段基本一致，仅 `status` 类型从 `ConversationStatus` Enum 退化为 `str` |

| `ConversationListResponse` | `ConversationListResponse` | 完全一致 |
| `CreateConversationRequestModel` | `CreateConversationRequest` | 一致 |

| `UpdateConversationRequestModel` | `UpdateConversationRequest` | 一致 |

**影响**: 前后端契约分裂，任何字段变更需同步修改两处，已违反 AGENTS.md §4.1 "前后端共享的数据结构必须同源定义"。

**修复建议**: 从 `harness/models/conversation.py` 直接导入模型到 schemas.py（或直接用域模型装饰 response_model），删除 API 层重复定义。前端 TypeScript 类型应通过 OpenAPI 从后端 Pydantic 模型自动生成。

### P0-2: 多个 Conversation API 端点缺少 `response_model` — OpenAPI 文档不完整

**文件**: `harness/api/routes.py`

以下端点未设置 `response_model`，导致前端无法通过 `npm run generate-api:types` 自动生成 TypeScript 类型：

| 端点 | 行号 | 返回结构 |
|---|---|---|
| `POST /api/v1/conversations` | `harness/api/routes.py:369` | `{conversation_id, title, created_at}` |
| `POST /api/v1/conversations/{id}/messages` | `harness/api/routes.py:451` | `{run_id, conversation_id, seq}` |
| `DELETE /api/v1/conversations/{id}` | `harness/api/routes.py:494` | `{success: bool}` |
| `PATCH /api/v1/conversations/{id}` | `harness/api/routes.py:507` | `{success: bool}` |

**影响**: 前端 `schema.ts` 自动生成不会包含这些端点的响应类型，前后端契约不对齐。违反 AGENTS.md §4.1。

**修复建议**: 每个端点添加 `response_model=...`：
- `POST /conversations` → `CreateConversationResponse`（已在 models 中定义）
- `POST /{id}/messages` → `SendMessageResponse`（已在 models 中定义）
- `DELETE /{id}` → `DeleteConversationResponse`（需新增，含 `success: bool`）
- `PATCH /{id}` → `UpdateConversationResponse`（需新增，含 `success: bool`）

### P0-3: `_write_assistant_message` 异常被完全静默吞没

**文件**: `harness/api/deps.py:143-144`

```python
        except Exception:
            pass
```

助手消息写入失败时（EventStore 异常、conversation 不存在等）完全无日志记录，静默失败。这属于受信组件内部的故障被掩埋。

**影响**: 运行中 conversation 的 assistant 消息可能丢失，运维无法感知，违反 AGENTS.md §6.1 "受信组件内部异常不得泄漏到非受信层，必须转换为结构化错误事件写入 Event Store"。当前实现既不写事件，也不打日志。

**修复建议**: 至少添加 `_log.exception("Failed to write assistant message for run=%s", run_id)` 日志。更严格的方案是写入 `ToolFailed` 或独立错误事件。

### P0-4: Conversation 事件与 Run 事件共享 `run_id` 列空间

**文件**: `harness/storage/event_store.py:475-476`

```python
async def get_events_for_conversation(self, conversation_id: str) -> list[Event]:
    return await self.get_events(conversation_id)
```

Conversation 事件（`ConversationStarted`, `ConversationMessage` 等）使用 `conversation_id` 作为 `events` 表的 `run_id` 值存储。这意味着：
1. Conversation 事件和 Run 事件在同一列空间，无法区分
2. 无法通过 SQL 查询"属于某 conversation 的所有 Run 事件"（只能查 conversation 自身的事件）
3. `list_runs()` 查询可能意外返回 conversation 行

**影响**: 违反 conversation_dev_plan.md §2.3 设计（原本要求新增 `events.conversation_id` 列），数据模型混用会在后续 Phase（如按 conversation 查询 Run 列表）造成查询歧义。

**修复建议**: 按 dev_plan 设计，给 `events` 表新增 `conversation_id` 可为空列：
```sql
ALTER TABLE events ADD COLUMN conversation_id TEXT;
CREATE INDEX IF NOT EXISTS idx_events_conversation ON events(conversation_id);
```
Run 事件写入时填入关联的 `conversation_id`，Conversation 级别事件保持 `run_id = conversation_id`。

## 🟡 P1 建议修复

### P1-1: `_build_conversation_context` 使用裸 dict 访问而非 Pydantic 模型

**文件**: `harness/models/conversation.py:74-78`

### P1-3: Conversation 列表只返回 `active` 状态 — 软删除后对话不可见

**文件**: `harness/storage/event_store.py:402-412`

```python
"""SELECT * FROM conversations WHERE status = 'active' ..."""
```

当前 `list_conversations()` 和 `total_conversation_count()` 硬编码 `WHERE status = 'active'`，`delete_conversation` 是软删除（标记为 `archived`）。这意味着用户删除对话后完全无法恢复（即使数据仍在表中）。

**影响**: 对话删除后没有恢复机制（既无 trash bin，也无 undo）。与 conversation_dev_plan.md §7.3 回退方案不匹配。

**修复建议**: 要么提供 `include_archived` 查询参数，要么前端单独提供 recovery API。当前最小修复：增加 `GET /api/v1/conversations?include_archived=true` 查询参数。

### P1-4: 前端 `event_type` 为 `string`，无 TypeScript 枚举

**文件**: `frontend/src/hooks/useRunWebSocket.ts`、`frontend/src/components/ConversationDrawer.tsx` 等多处

所有事件类型在前端均为 `string` 类型，散布在 `switch` 语句和字符串比较中。后端新增事件类型（如 `RunOrphaned`）时，前端无编译期保护。

**影响**: 违反 AGENTS.md §6.2 "共享 Schema 自动生成类型定义"。当前 `npm run generate-api:types` 生成的 `schema.ts` 仅覆盖 API 响应结构，不覆盖事件类型枚举。

**修复建议**: 在后端 `EventType` Enum 上使用 `from enum import Enum` 的 `.value` 列表，通过 OpenAPI 的 `schema` extra 或自定义端点导出完整事件类型列表，前端据此生成 TypeScript `type EventType = "RunStarted" | "AgentThought" | ...`。

### P1-5: Conversation 事件缺少 `ConversationEndedPayload` 的 `model_dump()` 校验调用

**文件**: 全局搜索 — `CONVERSATION_ENDED` 事件类型已定义但无任何写入点

`EventType.CONVERSATION_ENDED` 已定义且已有 Payload Model 和 PAYLOAD_MODEL_MAP 注册，但全代码库无一处调用 `append_event(..., EventType.CONVERSATION_ENDED, ...)`。Conversation 结束时缺少正式结束事件。

**影响**: 对话无明确的终止标记，下游依赖此事件的逻辑（如对话存档、清理）无法触发。PRD §5.1 要求写入 `ConversationEnded` 事件。

### P1-6: `_build_conversation_context` 内容截断可能切断多字节字符

**文件**: `harness/models/conversation.py:78`

```python
messages.append(f"[{role}] {content[:500]}")
```

Python 字符串切片按字符截断，对 ASCII/中文安全，但 `[:500]` 可能截断 emoji 或其他多码点序列（如 👨‍👩‍👧，一个 grapheme 由多个 code point 组成）。

**影响**: 低概率，仅在 content 恰好以组合 emoji 结尾时出现。但值得在截断工具函数中统一处理。

## 结论

**需修复后再合并** (🔴 P0 × 4).

当前实现完成了 Phase 1 多轮对话的核心功能（Conversation CRUD + 上下文注入 + assistant 消息自动写入 + 前端 ConversationView），625 项测试全部通过。但存在 4 个 P0 问题必须修复：

1. **Schema 重复定义**（P0-1）— 影响前后端契约的单一来源原则
2. **缺少 response_model**（P0-2）— OpenAPI 文档不完整
3. **异常静默吞没**（P0-3）— 受信组件行为不可观测
4. **Conversation 事件与 Run 事件混用 run_id 列**（P0-4）— 数据模型歧义

建议先修复 P0-1（消除 Schema 重复）和 P0-2（补 response_model），这两项修复后可立即确认 OpenAPI 输出正确。P0-3 和 P0-4 可在同一 PR 中修复。

前端方面：Phase 4 UI 组件实现超出 Phase 1 范围（dev_plan 中 Phase 1 前端仅做 API 适配），但 ConversationDrawer 等组件整体质量可接受，暂时保留不阻塞合并。
