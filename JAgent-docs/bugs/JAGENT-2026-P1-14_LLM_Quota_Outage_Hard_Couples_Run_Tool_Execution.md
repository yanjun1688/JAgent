# JAGENT-2026-P1-14 在线 LLM 配额失效时 run/tool 执行层直接 403,无降级/熔断

## 状态

未修复（渗透测试发现，2026-10-12）

## 发现方式

渗透测试：对本地 Docker 部署实例施加"LLM 配额耗尽"条件，观测整条执行链的行为。

## 影响

JAgent 的"决策"与"工具执行"强耦合于在线 LLM。规划（plan）、交付契约抽取、修订（revise）、步骤本地修复等每一轮都需要调用 LLM。一旦上游返回配额/欠费类 **403**，run/tool 层不再有可用的决策来源，整条执行链停摆。

系统没有为"LLM 不可用"提供降级、熔断或明确的终态收敛，表现为**直接 403**——既不可用，也不可观测（未收敛为结构化 `Run/failed` 事件时）。

## 复现

1. 配置一个 key 格式正确但**配额耗尽/欠费**的 LLM 端点（或临时把 `LLM_API_KEY` 换成欠费 key），`docker compose up -d`，后端进入 Real LLM 模式。
2. 匿名 `POST /api/v1/runs` 创建 Run。
3. 观察：上游 LLM 调用返回 403，run/tool 执行层随之 403。

## 实际结果

上游 LLM 返回非 200（观测为 403）后，`harness/core/llm_client.py:246-248` 的 `resp.raise_for_status()` 抛出 `HTTPStatusError` 并向上传播，执行链中断。

## 预期结果

- LLM 不可用 / 配额耗尽应被**受信层**捕获并收敛为结构化终态事件（如 `Run/failed` + 可判别 phase），而非裸 403 冒泡到执行链；
- 应具备熔断/降级：至少停止继续调度、返回可解释错误，且**不依赖 Agent 配合**（AGENTS.md §2.1）；
- 错误面向操作员可解释，能区分"配额耗尽"与"程序缺陷"。

## 根因定位

- `harness/core/llm_client.py:246-248`：非 200 一律 `raise_for_status()`，未区分**配额/限流/鉴权**类错误，无重试/熔断分类（`timed_chat` 仅记日志后原样 re-raise）。
- **执行链对 LLM 的强耦合**：Planner 每轮 plan/revise 均需 LLM，无 LLM 时不存在确定性降级路径。这是"非受信组件不可用 → 受信执行链裸崩"的可用性面缺口。
- 需确认 Scheduler 是否将 `HTTPStatusError` 规约为 `RunFailed`；若否，应补受信层"外部异常 → 事件收敛"（参照 AGENTS.md §6.1 错误处理要求）。

## 证据缺口（待复现确认）

- 403 的**具体传播路径**需固化：是 `POST /runs` 请求本身 403，还是 run 记为 `Run/failed`？以事件流原始证据为准。
- 需补：上游 401/403/429/超时的错误分类与受信层收敛**测试（故障注入）**。

## 受信边界说明

LLM 属**非受信组件**。按 Harness 范式，非受信组件的不可用不应让受信执行链"裸崩"——受信层应把外部失败收敛为事件、并给出确定性行为。本项即该缺口。
