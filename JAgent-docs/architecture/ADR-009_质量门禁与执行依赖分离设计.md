# ADR-009 质量门禁与执行依赖分离设计

> **版本**: v1.1
> **日期**: 2026-08-13
> **状态**: 已实施（Q-01~Q-08 全部落地；Q-01/Q-03/Q-04 经核查确认维持现状）
> **关联**: `ADR-008_交付契约与完成语义分层.md` · `JAGENT-2026-Completion-INDEX.md`

---

## 1. 背景

上一轮架构审查确认了四个概念需要从职责上彻底分离，避免"用户要求"、"LLM 自检"、"执行顺序"、"最终验收"互相污染：

| 概念 | 现在的载体 | 问题 |
|------|-----------|------|
| 用户要求 / 最终验收 | `DeliveryContract` | 被误以为与 `depends_on` 重复 |
| LLM 计划自检 | `DagPlan.required_operations` | 命名易被误当作系统真实要求 |
| 执行顺序 / 数据依赖 | `DagStep.depends_on` | 唯一真正负责调度 |
| 完成判定 | `CompletionVerdict` | 需要明确只信 `DeliveryContract + StepResult` |

同时确定了两个生命周期简化决策：

- **总计时器**：整个 Run 只有一个全局 deadline，各阶段共享剩余时间，不再维护多套独立 phase timeout。
- **无需确认过期**：不给 confirmation 增加过期规则；确认等待是 Run 总预算的一部分。

## 2. 决策（Q-01 ~ Q-08）

| 编号 | 主题 | 冻结结论 | 实施状态 |
|------|------|----------|----------|
| Q-01 | DeliveryContract 定位 | **保留**。它是用户要求的唯一权威载体 + 系统最终验收标准（可信）。不参与调度，不读 Answer，不读 LLM `task_state`。 | **已确认**（核查符合现状） |
| Q-02 | LLM 计划自检 | `Plan.required_operations` **改名 `declared_operations`**，明确是 LLM 自检声明（不可信）。只能用于审查 LLM 计划自洽、生成修复反馈、审计。不能用于：创建交付契约、授权新副作用、替代 DeliveryContract、决定最终完成。 | **已实施** |
| Q-03 | 唯一执行依赖 | 执行顺序/数据依赖**只由 `DagStep.depends_on` 表达**。不再有第二套执行依赖模型。 | **已确认**（核查符合现状） |
| Q-04 | 完成门边界 | `CompletionGate` **只信 `DeliveryContract + StepResult`**。`deliverable_met` 逐条对照契约；空契约 → `unverified`；绝不因 LLM/Answer 表述而宣称完成。 | **已确认**（核查符合现状） |
| Q-05 | `DeliveryContract.after` | **删除该字段及执行语义**。契约不再承载时序职责；时序归 `depends_on`。 | **已实施** |
| Q-06 | mutating 覆盖 | 修订中新增 mutating 步骤**必须由 DeliveryContract 覆盖**，不得仅因 LLM 在 `declared_operations` 自报而被授权（堵 self-authorize 漏洞）。 | **已实施** |
| Q-07 | 总计时器 | Run 全局 `run_timeout_ms` 是唯一总预算（0=禁用）。各阶段（plan/revise/tool/answer/classify）与等待（pause/confirm）使用剩余时间；工具层保留 `min(tool_timeout, remaining)` 保护。移除 `phase_timeout_ms`。 | **已实施** |
| Q-08 | 无需确认过期 | 不给 confirmation 增加 TTL/expires 字段。确认等待纳入 Run 总预算；`run_timeout_ms=0` 时保留等待兜底上限（`confirm_timeout_ms`/`pause_timeout_ms`）。 | **已实施** |

## 3. 四层模型（目标结构）

```text
┌─────────────────────────────────────────────┐
│ 1. 用户要求层  DeliveryContract             │  可信、不可变、落事件
│    回答：用户要求交付什么                     │
├─────────────────────────────────────────────┤
│ 2. LLM 计划层   PlanCandidate               │  不可信、LLM 输出
│    declared_operations = LLM 自检声明        │
│    回答：LLM 计划怎么做                       │
├─────────────────────────────────────────────┤
│ 3. 执行层       ValidatedPlan / DagPlan     │  受信 PlanGuardrail 校验
│    DagStep.depends_on = 唯一执行依赖         │
│    回答：按什么顺序执行                       │
├─────────────────────────────────────────────┤
│ 4. 验收层       CompletionGate              │  只信 DeliveryContract + StepResult
│    回答：交付是否真正达成                     │
└─────────────────────────────────────────────┘
```

### 3.1 各层职责边界

| 组件 | 负责什么 | 不负责什么 |
|------|----------|-----------|
| `DeliveryContract` | 用户真正要求什么 | 不负责调度、不读 Answer |
| `PlanCandidate.declared_operations` | LLM 自检声明 | 不定义用户要求、不授权副作用 |
| `PlanGuardrail` | 拒绝非法/不覆盖契约的计划 | 不依赖 LLM 自觉 |
| `DagStep.depends_on` | 唯一执行顺序和数据依赖 | 不代表交付完成 |
| `ToolExecutor` | 执行真实副作用 | 不宣布 Run 完成 |
| `StepResult` | 记录真实执行结果 | 不读取 task_state |
| `CompletionGate` | 最终质量门禁 | 不猜用户意图 |
| `Answer` | 展示系统判定结果 | 不参与状态判定 |

## 4. 质量门禁检查链（Q-02/Q-04/Q-06 目标）

### 4.1 PlanGuardrail 六道检查（待实现后完整形态）

1. **结构检查**：step ID 唯一、依赖存在、无自依赖、无环、input 是对象。
2. **工具契约检查**：tool 存在、schema 合法、operation 存在、probe 合法、引用字段合法。
3. **唯一依赖检查**：只认 `DagStep.depends_on`。
4. **DeliveryContract 覆盖检查**：每条契约必须匹配至少一个计划步骤（**直接查契约，不查 declared_operations**）。
5. **副作用覆盖检查**：mutating step 必须被 DeliveryContract 覆盖（Q-06）。
6. **输出引用检查**：`$step.field` 存在、字段允许、依赖一致。

### 4.2 完成门判定（当前已实现）

```text
无 DeliveryContract            → unverified
有契约且全部 met              → met（deliverable_met=true）
有契约且任意 unmet            → failed（deliverable_met=false）
```

判定依据只有：

- `state.delivery_contracts`（用户要求）
- `StepResult.step_normal`（实际执行结果）

## 5. 生命周期简化（Q-07/Q-08，本轮已实现）

### 5.1 总计时器语义

```text
Run 开始
→ 记录 deadline = now + run_timeout_ms（0 = 不启用）
→ 每个阶段/等待读取剩余时间
→ 时间耗尽 → PHASE_TIMED_OUT → 统一取消与回收 → RunFailed
```

- `SchedulerConfig.phase_timeout_ms` 已移除。
- `run_timeout_ms` 是唯一总预算。
- `cancel_grace_ms` 是清理时间，不计入执行预算。
- 工具层保留自身 `timeout_ms`，实际生效为 `min(tool_timeout_ms, run_remaining)`。

### 5.2 等待语义（无"过期"概念）

- confirmation / pause 不引入 TTL 或 expires 字段。
- 等待上限 = `min(confirm_timeout_ms 或 pause_timeout_ms, run_remaining)`。
- `run_timeout_ms=0` 时，等待使用原有兜底上限（默认 300s），保持行为兼容。

| 变更 | 影响 | 处理 |
|------|------|------|

## 7. 记录在案的限制（延续 L-01/L-02）

- **L-01 时序语义**：由 Q-03/Q-05 替代——时序归 `depends_on`，不再由契约承载。`after` 字段删除后该项关闭。
- **L-02 内容匹配**：`content` 存底但不参与匹配；内容级验证仍留后续。

设计总思想：将系统分成“用户要求、执行计划、实际结果、最终回答四层完全分离”。
核心原则：
LLM 可以提出计划，但不能定义用户要求；
系统可以校验计划，但不能替用户猜要求；
Tool 可以产生结果，但不能宣布任务完成；
只有完成门可以决定是否完成。
一、四层模型
1. 用户要求层：DeliveryContract
这是唯一的权威交付标准。
class DeliveryContract(BaseModel):
    contract_id: str
    source: Literal["caller", "extracted"]
    tool: str
    input: dict[str, Any]
例如：
{
  "contract_id": "c1",
  "tool": "file_op",
  "input": {
    "operation": "write",
    "path": "x.txt",
    "content": "hello"
  }
}
它代表：
用户要求系统完成什么。
它必须：
- 在 RunStarted 或 DeliveryContractsResolved 时落 EventStore；
- 之后不可被 Planner/Reviser 改写；
- 不包含执行顺序字段；
- 不读取 Answer；
- 不读取 LLM 的 task_state。
DeliveryContract 是“验收单”，不是执行计划。
2. LLM 计划层：PlanCandidate
LLM 输出的计划应该明确被视为“不可信候选”。
class PlanCandidate(BaseModel):
    intent: str
    steps: list[DagStep]
    declared_operations: list[DeclaredOperation] = []
建议把现在的：
required_operations
改名为：
declared_operations
因为 required_operations 这个名字会让人误以为它是系统真正的用户要求。
它实际表示：
LLM 自己认为这个计划应该覆盖哪些操作。
它只能用于：
- 审查 LLM 计划是否自洽；
- 给 LLM 生成修复反馈；
- 记录审计信息；
- 辅助调试。
它不能用于：
- 创建用户交付契约；
- 授权新的副作用；
- 替代 DeliveryContract；
- 决定最终完成。
3. 受信计划层：ValidatedPlan
PlanGuardrail 不应该只是返回一串错误，理想上应该把候选计划转换为受信计划：
class ValidatedPlan(BaseModel):
    intent: str
    steps: list[DagStep]
    contract_bindings: dict[str, list[str]]
其中：
contract_id → matching step_id
例如：
{
  "c1": ["s1"],
  "c2": ["s2"]
}
这样系统明确知道：
DeliveryContract c1 由步骤 s1 负责
DeliveryContract c2 由步骤 s2 负责
ValidatedPlan 只能由受信组件生成，不能由 LLM 直接构造。
二、PlanGuardrail 应该分成六道检查
第一道：结构检查
检查：
- step ID 唯一；
- 依赖存在；
- 无自依赖；
- 无循环；
- input 是对象；
- step ID 和引用格式正确。
第二道：工具契约检查
检查：
- tool 是否存在；
- input 是否符合工具 schema；
- operation 是否存在；
- probe 是否允许；
- 引用字段是否允许；
- 危险操作是否符合规则。
第三道：唯一依赖检查
只保留：
DagStep.depends_on
它负责：
- DAG 拓扑；
- 执行顺序；
- 下游跳过；
- 上游输出可用性；
- Reviser 重建计划。
不再使用：
DeliveryContract.after
第四道：DeliveryContract 覆盖检查
这是最重要的一道。
系统使用可信的 DeliveryContract检查计划：
每一条 DeliveryContract
    必须能匹配到至少一个计划步骤
不是检查：
Plan.required_operations 是否匹配 steps
而是检查：
DeliveryContract 是否匹配 steps
因为只有 DeliveryContract 代表用户真实要求。
如果用户要求：
write x.txt
但 Planner 只返回：
read x.txt
PlanGuardrail 应该直接拒绝这个计划，而不是等执行完后才发现。
第五道：副作用覆盖检查
任何 mutating step：
write
delete
POST
browser click
run_code
必须满足：
它被 DeliveryContract 覆盖
不能满足于：
LLM 自己在 declared_operations 中写了它
否则 Reviser 可以通过自我声明给新的副作用“授权”。
第六道：输出引用检查
检查：
- 引用的步骤存在；
- 引用字段存在；
- 字段允许被引用；
- 上游步骤与当前依赖关系一致；
- 不允许通过普通字符串绕过静态校验。
三、执行阶段只信实际 StepResult
Executor 执行后生成：
class StepResult(BaseModel):
    step_id: str
    exec_state: ExecState
    output: Any = None
    error: str | None = None
系统只关心：
- 是否真的执行；
- 是否成功；
- 是否是 probe；
- 是否有实际输出；
- 是否可以重试。
不读取：
LLM task_state
LLM 说“已完成”
Answer 内容
task_state 只能作为审计信息。
四、完成门分成两个维度
机械执行完成
检查：
计划中应该正常完成的步骤是否正常完成
主要用于识别：
- FAILED；
- UNSUCCESSFUL；
- SKIPPED；
- 未执行步骤。
用户交付完成
检查：
每一个 DeliveryContract 是否都有正常完成的匹配步骤
伪代码：
for contract in state.delivery_contracts:
    bound_steps = bindings[contract.contract_id]

    if not any(results[sid].step_normal for sid in bound_steps):
        return DeliverableUnmet(contract.contract_id)
最终结果：
无 DeliveryContract
    → unverified

有 DeliveryContract，全部满足
    → met

有 DeliveryContract，任意一条不满足
    → failed
只有这里通过，才能写：
RunCompleted
Answer 只能读取这个最终状态。
五、反馈和修复循环
计划生成错误
例如：
DeliveryContract 要 write
Plan 没有 write step
流程：
PlanGuardrail 拒绝
→ 生成结构化错误
→ Planner 重试
这是计划生成阶段重试。
计划执行失败
例如：
write 因权限失败
流程：
ToolFailed / StepResult.failed
→ Scheduler 生成执行反馈
→ Reviser 生成替代计划
→ 合并计划
→ 再次 PlanGuardrail
→ 重新执行
最终交付仍不满足
如果所有修复都失败：
DeliveryContract unmet
→ RunFailed
绝不能让 Answer 说：
“虽然没有写入，但任务完成了”
六、最终职责表
组件
DeliveryContract
PlanCandidate
PlanGuardrail
depends_on
ToolExecutor
StepResult
CompletionGate
Answer
七、最终建议
我建议最终收敛为：
DeliveryContract
    保留，作为系统质量门禁

Plan.required_operations
    改名 declared_operations
    只作为 LLM 自检和审计

DagStep.depends_on
    作为唯一执行依赖

DeliveryContract.after
    删除执行语义，最好从模型中移除

CompletionGate
    只信 DeliveryContract + StepResult
一句话总结：
DeliveryContract 解决“用户要的是否完成”；  
depends_on 解决“步骤按什么顺序执行”；  
declared_operations 只解决“LLM 自己的计划是否自洽”。  
三者保留，但不能混用。
