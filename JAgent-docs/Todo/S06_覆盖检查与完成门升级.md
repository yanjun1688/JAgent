## 2. 问题背景

现状（JAGENT-2026-P1-13）：
- `step_normal` 只表示"工具调用机械成功"，不表示"用户要求的文件已创建、内容正确、回读验证完成"。
- 日志 `RunCompleted(all_normal=true, unmet_step_ids=[])`（harness.log）掩盖交付未达成——list 空目录也能让 `step_normal` 通过。
- `_completion_gate` 的 required_operations 检查基于 LLM 自报，弱模型自洽少报时无法察觉（C-02 明示：这是缓解不是根治）。

必须分离两维状态（INDEX §验收项 7）：
- `mechanical_complete`：系统机械执行完成（全 step_normal）。
- `deliverable_met`：交付契约已验证达成。
不再用单一 `RunCompleted` 掩盖交付未验证。

## 3. 为什么这么做

- D-03：交付达成 = 契约中每条 operation+path 都有匹配 step 且 step_normal。
- D-04：无契约 / 契约未验证 → 如实标记 unverified，绝不假绿。
- C-06：`DeliverableVerification` 只对照已存在契约验证，不推断用户意图。

## 4. 做之前先检查影响范围

- `_completion_gate` 调用点（`scheduler/plan.py`）：642、726、835、851——全部改为同时产出两维结果。
- `RunCompletedPayload` 消费方：`fold.py:255-262`、`api/routes.py`（RunDetail）、前端 `RunDetail.tsx`（展示 `all_normal`）。
- `_finalize_with_summary`（`scheduler/plan.py:1187-1218`）签名扩展。
- 测试：`tests/test_completion_gate.py`、`tests/test_step_normal_gate.py`、`tests/test_probe_and_convergence.py`、`tests/test_exec_state_mapping.py`。
- **兼容**：`RunCompletedPayload` 新增字段带默认值（`deliverable_met: bool | None = None`、`deliverable_status: Literal["met","unverified","failed"] = "unverified"`），旧事件可解析。

## 5. 期望达到的目标

- `_completion_gate` 升级为双输出：

```python
@dataclass
class CompletionVerdict:
    mechanical_complete: bool
    unmet_step_ids: list[str]
    deliverables: list[DeliverableVerdict]   # 每条契约的判定
    deliverable_met: bool                    # 全部契约 met
    deliverable_status: str                  # "met" | "unverified" | "failed"

@dataclass
class DeliverableVerdict:
    contract_id: str
    status: Literal["met", "unmet", "unverified"]
    matched_step_ids: list[str]              # 达成该契约的 step（供审计）
```

- 判定规则（D-03）：
  - 每条契约：存在 `RequiredOperation.step_satisfies(step, contract)` 且该 step 的 `step_normal=True` → `met`；否则 `unmet`。
  - 空契约（旧请求）→ `deliverable_status="unverified"`（D-04）。
- `RunCompletedPayload` 新增：`deliverable_met`、`deliverable_status`、`deliverable_summary`。
- 完成门逻辑：`mechanical_complete` 不通过 → 依旧 `_fail`（禁止假绿）；`mechanical_complete` 通过但 `deliverable_status="unverified"` → `RunCompleted` + 显式标记；`deliverable_met=False`（契约存在但未达成）→ 若 mechanical 也不全 → `_fail`；边界情况按 C-02 以"绝不宣称交付达成"为准。

## 6. 实现要点

- `DeliverableVerification`（受信校验器，C-06）实现为纯函数：输入 `contracts` + `results` + `plan`，输出 `list[DeliverableVerdict]`。**只对照契约验证，不生成契约**。
- `mechanical_complete` 仍由全 step_normal 聚合（保留现有 `_completion_gate` 的机械部分）。
- fold 分支：`RunCompletedPayload` 新字段 → `RunState.completion_evidence` 扩展。
- **禁止事项**：
  - 禁止让 LLM 的 `task_state` 影响 deliverable 判定（约束 4）。
  - 禁止在内容未匹配校验实现前宣称 `deliverable_met=True` 代表内容正确（D-03 明确只到操作+路径级，文档记录 L-02）。
  - 禁止 `DeliverableVerification` 推断用户意图（C-06）。

## 7. 验收标准

1. 新增测试 `tests/test_deliverable_gate.py`：
   - 契约 [write blackbox.txt, read blackbox.txt]，计划含两 step 且都 normal → `deliverable_met=True`。
   - 契约含 write，计划只有 read（write 丢失）→ write 契约 `unmet`，`deliverable_met=False`，且机械门若全 normal 也**不得**宣称 deliverable 达成。
   - 契约要求 `path=blackbox.txt`，step 路径被 Reviser 改成 `other.txt` → `unmet`（路径级校验生效）。
   - 契约要求 write，step 换成 list（观察替代交付）→ `unmet`（禁止 fake-green，测试要求 4）。
   - 空契约 → `deliverable_status="unverified"`，Run 仍可 completed 但带标记。
   - 多契约部分达成 → 全部达成才 `met`（D-05）。
2. 现有 `tests/test_completion_gate.py`、`tests/test_step_normal_gate.py` 回归全绿（新增字段默认值不破坏断言）。
3. 端到端（fake LLM）：用户"创建+读取 blackbox.txt"，Planner 只给 read → Run 不得 `deliverable_met`（测试要求 1）。
4. 事件链：`RunCompleted` payload 含 `deliverable_status`，fold 后可读。

## 8. 这么做的后果

- **对 S08**：Reviser 限权以 S05 契约 + 本步判定为基准。
- **对 S07**：API caller 契约与 `source` 标记进入判定路径。
- **对 S12**：验收项 2（契约不依赖弱模型）、7（双维分离）、10（事件重放）依赖本步。
- **前端影响**：`RunDetail` 展示 deliverable 状态（S12 前可为后端就绪，前端展示可后续补）。
- **行为变化**：部分此前"机械成功即 completed"的 Run 现在会标记 unverified 或失败——预期改进，回归留意。
