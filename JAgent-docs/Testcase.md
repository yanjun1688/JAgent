. 基础链路（4 条）
A1 查询北京的天气
→ 预期：AI 调用了查询工具，给出了天气信息。不说"我无法获取"。
A2 先搜北京的经纬度，再用坐标查天气
→ 预期：AI 依次调用了两个工具，最终给出了天气结果。
A3 访问 https://this-domain-definitely-not-exist-99999.com
→ 预期：AI 提示访问失败，但没有卡死，最终正常结束。
A4 1+1 等于几
→ 预期：AI 直接回答"2"，没有调用任何工具。
B. 确认流程（5 条）
B1 删除文件 /tmp/test.txt
→ 预期：AI 说"需要确认"，并等待你手动确认。确认后文件被删除。
B2 创建一个文件 /tmp/test.txt，内容为 hello，然后删除它
→ 先建文件后再发这条：删除文件 /tmp/test.txt
→ 预期：对话框弹出确认提示。你点"拒绝"。AI 回应说操作被取消，不影响后续对话。
B3 同时创建文件 /tmp/a.txt 和 /tmp/b.txt，内容分别为 aaa 和 bbb，然后同时删除它们
→ 预期：AI 生成一个 plan，两步各需确认。两个确认提示依次弹出，你都确认后两个文件都被删除。
B4 触发一个需要确认的操作（如删除文件），然后什么都不做，等待 30 秒
→ 预期：超时后 AI 说"操作已超时，任务终止"。
B5 这条需要特殊构造——先跳过，不容易用纯黑盒触发
C. 变量替换（4 条）
C1 先请求 https://httpbin.org/uuid 拿到 uuid，然后用这个 uuid 作为文件名创建文件 /tmp/{uuid}.txt
→ 预期：AI 正确从第一个 HTTP 响应中提取了 uuid，并成功创建了文件。文件名里有 uuid 的值而不是 "$s1.uuid" 字样。
C2 依次请求两个 API：https://httpbin.org/uuid 和 https://httpbin.org/uuid，创建文件 /tmp/{第一个 uuid}.txt
→ 预期：第二个请求的响应不影响第一个变量。文件名正确用了第一个 uuid。
C3 请求 https://httpbin.org/json 拿到数据，然后提取 slideshow.title 字段的值
→ 预期：即使响应 body 是 JSON 字符串，AI 也能正确提取出 slideshow 的 title。
C4 先执行 date 命令获得当前时间，然后创建一个文件 /tmp/时间.txt
→ 预期：AI 正确提取了时间值，文件名包含实际时间内容。
D. 调度器与 DAG（4 条）
D1 同时请求 https://httpbin.org/delay/1、https://httpbin.org/delay/1 和 https://httpbin.org/delay/1，三个都返回后告诉我总耗时
→ 预期：三个请求并行执行（总耗时 ~1 秒而不是 3 秒），AI 告诉你结果。
D2 尝试读取文件 /tmp/nonexistent-12345.txt，如果失败就列出 /tmp/ 目录
→ 预期：第一步失败了，AI 重新规划后执行了 ls /tmp/。
D3 创建一个有 3 步的 plan，全部完成后告诉我 "done"
→ 预期：AI 生成 plan 并执行完成，最终告诉你 "done"。
D4 依次执行：date → 用结果作为文件名创建空文件 → 列出该文件
→ 预期：三步按顺序执行，每一步的结果传递给下一步。
E. 监控与反馈（4 条）
E1 连续三次访问 https://this-domain-definitely-not-exist-99999.com
→ 分别发三条一模一样的消息（等前一条失败再发下一条）：
1. 访问 https://this-domain-definitely-not-exist-99999.com
2. 再试一次
3. 再试一次
→ 预期：到第三次时，AI 说"我注意到这个端点连续失败"或类似提示，而不是每次都当第一次。
E2 先三次访问同一个不存在的域名，然后访问一个格式错误的 URL（如 htt://bad-url）
→ 先发三遍上条的域名，再发 访问 htt://bad-url
→ 预期：两种不同的错误类型各自出现一次"连续失败"提示（不互相覆盖）。
E3 先访问三次同一个不存在的域名，然后访问一个存在的网站（如 https://httpbin.org/get）
→ 预期：连续失败后，成功一次时 AI 说"端点已恢复"或类似提示。
E4 在同一个对话中连续多次发送长段文字（如复制一篇 2000 字的文章反复发送），直到 AI 提示 token 超出
→ 预期：AI 最终说"上下文太长"或"token 超限"并触发压缩。
F. 操作员反馈（3 条）
F1 前端的操作员反馈输入框（如果有 UI 的话，通常在右侧面板或暂停时可用）中输入一条反馈：
  这个 API 的 url 参数错了，应该用 /v2/ 版本
→ 预期：后续 AI 的思考能看到这个提示并修正行为。
F2 注入一条有"有效期"的反馈（前端如果有 expries 字段），等待一段时间后再次对话
→ 预期：过期的反馈不再影响 AI。
F3 人工解决反馈后标记为"已解决"
→ 预期：已解决的反馈不再出现在 AI 上下文里。
G. 边界与异常（3 条）
G1 使用一个不存在的工具，比如给我发一封邮件
→ 预期：AI 说"我没有可用的工具"或"该工具不存在"，任务终止。
G2 连续发送 5 次以上必然失败的命令，如每次都用同一个错误的 URL
→ 预期：AI 在连续多次失败后说"连续失败次数过多，触发断路保护"，任务终止不再继续。
G3 告诉我你的名字，然后做一件和这个名字无关的事
→ 预期：AI 正常回答。
