## 2. 问题背景

日志证据：
- `watchdog_verify_stderr.log:84-86`：Run `1adff18c` 超时写 RunFailed，但 `pending_calls=1`——LLM/工具子任务未确认回收。
- `harness.log`：Run 1adff18c 卡在 `http_request` 60s，仅靠 Run 级 watchdog 兜底。
- 问题八：真实 LLM 调用可能 30s+，classify/plan/tool/revise/answer 多阶段叠加触发长尾；当前只有一个模糊总超时，无法定位是哪一阶段超时、无法记录 provider 429/5xx/连接等待。

根因：无分阶段预算、无子任务取消集合、无宽限期、无 `pending_calls` 硬断言、无迟到事件拦截（后者 S09 已补）。

## 3. 为什么这么做

- 超时必须成为**受信的分阶段预算**，而不是只依赖一个总 Run timeout（问题八）。
- Watchdog 完成标准不是"写了 RunFailed"，而是"主任务和所有子任务都已进入可验证终态"（问题七）。
- C-03：取消 + 宽限期 await，禁止无限等待导致清理死锁。

## 4. 做之前先检查影响范围

- `SchedulerConfig` 消费方：`serve.py:139-142`、`tests/conftest.py`、各 scheduler 测试。
- `run()` 的 `wait_for` 取消语义：`asyncio.wait_for(task, timeout)` 会取消 task，但**不会** await 子任务链完成。
- LLM 调用点：`planner.plan/revise/classify/answer` 全部经 `self.planner.llm.chat`。取消需可传播（OpenAI/httpx 客户端 await 处）。
- Tool 调用：`ToolExecutor.execute`（`executor.py:135-591`）内部 `Sandbox.invoke`。
- MCP：`tools/mcp_call.py`、`mcp_manager.py`。
- `RunMonitor._pending_calls` 生命周期：ToolCalled 注册（`:161`）、ToolCompleted/失败移除（`:166`）。
- 测试：`tests/test_scheduler.py`、`tests/test_monitoring.py`、`scripts/test_real_llm_flow.py`。
- **性能**：分阶段超时预算要 >= LLM 单次真实耗时（30s+），否则误杀。

## 5. 期望达到的目标

- `SchedulerConfig` 增加分阶段预算：

```python
@dataclass
class SchedulerConfig:
    ...
    phase_timeout_ms: dict[str, int] = field(default_factory=dict)
    # {"classify": 15000, "plan": 60000, "revise": 60000, "tool": 60000, "answer": 45000}
    cancel_grace_ms: int = 5000     # C-03: 取消宽限期
```

- 阶段超时实现：每个阶段（classify/plan/revise/tool/answer）用 `asyncio.wait_for` 包裹，超时 → 写结构化事件（`PHASE_TIMED_OUT`，payload: phase, run_id, budget_ms），进入取消流程。
- 子任务注册表：维护 `run_id -> set[asyncio.Task]`（LLM task、tool task、MCP task）；watchdog/超时/取消时：
  1. 取消所有子任务；
  2. `await asyncio.wait(tasks, timeout=cancel_grace_ms)`；
  3. 宽限期后仍 pending → 写结构化 `TASK_CLEANUP_TIMEOUT`（C-03）并强制继续；
  4. 网络/MCP 连接显式 close（http_request `close_client`、backend.close）。
- `pending_calls` 硬性断言：`cleanup` 前（或后）若 `_pending_calls[run_id] > 0` → 写结构化告警事件；`cleanup` 之后 `pending_calls==0` 作为**目标**记录（C-03 已修正为"目标而非阻塞条件"）。
- 迟到事件：S09 已拦截，本步补`wait`期间不产生新的副作用（工具执行在取消后不得落盘）。

## 6. 实现要点

- 阶段计时器装饰器/上下文管理器（受信）：

```python
@contextmanager
def _phase_budget(run_id: str, phase: str, budget_ms: int):
    # 记录 phase 开始/结束/耗时；超预算标记 → 由调用方决定取消
```

- 取消实现：`run()` 的 watchdog 触发后调用 `await self._cancel_and_reap(run_id)`：

```python
async def _cancel_and_reap(self, run_id: str) -> None:
    tasks = self._phase_tasks.get(run_id, set())
    for t in tasks:
        if not t.done():
            t.cancel()
    if tasks:
        _, pending = await asyncio.wait(tasks, timeout=self.config.cancel_grace_ms / 1000)
        if pending:
            # C-03: 不无限等待，记录结构化事件
            await self.store.append_event(run_id, EventType.RESOURCE_CLEANUP_TIMEOUT, ...)
```

- LLM 客户端取消可传播性检查：`OpenAILLMClient.chat` 底层 await 是否响应 `asyncio.CancelledError`；不响应 → 加 `shield`+超时双保险。
- **禁止事项**：
  - 禁止无限 `await`（C-03）。
  - 禁止在取消后仍让工具写副作用（S09 拦截兜底 + 本步执行侧检查）。
  - 禁止把总 `run_timeout_ms` 删掉（保留作最后兜底）。
  - 禁止在 `cleanup` 中抛异常阻断 Run 终态（异常 → 结构化事件）。
