# S04 — 步骤输出引用契约（OutputRef 受信化）

> **主控**: `JAGENT-2026-Completion-INDEX.md`

## 2. 问题背景

日志证据（`harness.log:2629`、`harness.log:3583`、`harness.log:5013`）：
- Planner/Reviser 生成 `{"path": "$s1.result"}`。
- 现状：若 `s1` 输出无 `result` 字段 → 运行时 `VariableResolutionError` → step 失败（混乱）；若恰好命中不存在的字段语义，`$s1.result` 可能被当**普通文件路径**直接传给 `file_op`。

无契约的引用 = 三类风险：悬空 step、字段不匹配、字面量当路径。D-01 决定**支持但受信化**：语法层保留，规范层静态校验，执行层结构化解析。

## 3. 为什么这么做

- 把引用从"正则猜语义"升级为"声明 → 静态校验 → 结构化绑定"（INDEX §1.1 D-01 与 Port+Binding 模型）。
- 在 Executor 之前拒绝非法引用，避免运行时 `VariableResolutionError` 或字面量路径副作用。
- 为文件类工具的 `path/content` 明确禁引用（防止把 `$s1.result` 当路径写入文件系统）。

## 4. 做之前先检查影响范围

- 引用解析消费方：
  - `harness/core/dag_executor.py:469` `resolve_variables_in_input` 调用。
  - `harness/core/dag_vars.py` 全文（`_resolve_ref` / `substitute_vars` / `deep_resolve`）。
  - `harness/models/plan.py:108-133` `upstream_outputs`（旧式 selector 路径）。
- 测试：`tests/test_dag_executor.py`、`tests/test_probe_and_convergence.py`、`tests/test_scheduler.py` 中与 `$` 引用相关的用例。
- **兼容策略**：`dag_vars` 运行时解析**保留**作为执行层兜底；新增的 PlanGuardrail 静态校验在计划期先拦截明显非法引用。两处职责：Guardrail 管合法性，dag_vars 管解析（仅对已通过校验的引用）。

## 5. 期望达到的目标

- 新增 `OutputRef` 模型与解析函数（PlanGuardrail 内）：
  - 扫描每个 step 的 `input` 中所有 `$<step>.<field>` 或 `$<step>` 形式字符串；
  - 校验：引用 step 存在于 当前 plan ∪ completed ∪ available；
  - 校验：引用字段存在于被引用 step 对应 operation 的 `output_schema`（结构级，宽松：允许通配 `*` 或声明 `additionalProperties`，避免过度拒绝弱模型输出）；
  - 校验：目标 input 字段的 `ref_allowed == True`（C-04；缺省 False → 拒绝）；
  - 失败 → 返回结构化错误消息，进入 `_retry_prompt`，计划不进入 Executor。
- `file_op` 的 `path` / `content`、`http_request` 的 `url` 等字段默认禁引用（由 S02 声明）。

## 6. 实现要点

```python
class OutputRef(BaseModel):
    step_id: str
    field_path: str = ""        # "" = 整个输出
    # 仅内部表示，不要求 LLM 输出；LLM 仍写 "$s1.result"

def parse_output_refs(plan: DagPlan, *, registry: ToolRegistry) -> list[str]:
    """扫描并校验 plan 中全部 $ 引用。返回错误列表。空列表 = 合法。"""
```

- 解析规则（与 `dag_vars._resolve_ref` 的 regex 对齐）：`^\$(\w+)(?:\.([\w.]+))?$` 视为纯引用；内嵌 `prefix $s1.x` 也需扫描（`substitute_vars` 语义），但内嵌引用只校验 step 存在性，字段校验从宽。
- `output_schema` 校验用"浅层键集合"比对：取 schema 顶层 `properties` 键；若 schema 含 `additionalProperties` 则放行未知字段。避免对弱模型输出过度严格导致 Plan 无法生成。
- **禁止事项**：
  - 禁止让 Executor 直接拿未校验的 `$` 字符串当普通参数执行（本步后，凡含 `$` 的字符串进 Executor 前必须已过校验）。
  - 禁止要求 LLM 改输出格式（语法层保留 `$s1.result`，D-01）。
  - 禁止在本步引入结构化 `refs` 字段到 DagPlan（那是未来演进，INDEX L 记录，本轮不做）。

## 7. 验收标准

1. 新增单元测试 `tests/test_output_ref_validation.py`：
   - `$s1.result` 且 `s1` 在 plan 中、字段在 `s1` 的 output_schema 中、目标字段 `ref_allowed=True` → 通过。
   - 引用不存在的 step → 拒绝。
   - 引用字段不在上游 output_schema → 拒绝。
   - 目标字段 `ref_allowed=False`（如 `file_op.path`）→ 拒绝。
   - `$s1`（整体引用）→ 通过（若字段语义允许）。
   - 内嵌 `prefix $s1.x` → step 存在性校验。
2. `tests/test_dag_executor.py`、`tests/test_scheduler.py` 现有 `$` 引用用例回归全绿。
3. 验证：构造含 `$s1.result`（s1 为 list、无 result 字段）的计划 → `planner.plan` 重试而非 Executor 运行时报错。

## 8. 这么做的后果

- **对 S06**：非法引用计划在覆盖校验前已被拒，完成门只面对合法计划。
- **对 S08**：Reviser 生成的引用同样过 S04 校验（复用同一函数）。
- **行为变化**：此前"运行时才发现 $ 引用错误"的 Run 会提前在 Planner 阶段被纠正。留意回归中依赖"运行时错误路径"的用例。
- **技术债**：`dag_vars` 运行时仍保留 fuzzy fallback（`deep_resolve`），与静态校验可能产生轻微不一致——记录在案，后续统一。
