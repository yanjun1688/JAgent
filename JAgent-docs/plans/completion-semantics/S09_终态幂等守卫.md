# S09 — 终态幂等守卫（_fail/_complete + 迟到事件拦截）

> **所属层**: L3（Scheduler 生命周期）
> **关联**: `core/scheduler/base.py`（`_fail`/`_complete`/`run`）· `core/fold.py` · `storage/event_store.py`（append 路径）
> **决策编号**: C-05（终态幂等是前置）· D-06（终态后无迟到事件）· 问题七（资源回收）/ 问题八（重复终态）
> **主控**: `JAGENT-2026-Completion-INDEX.md`

---

## 1. 前置依赖

- **S05** 已完成：`RunState` 可折叠出 terminal 状态。
- 交付物快照（上游）：
  - `harness/core/scheduler/base.py:410-473` `_complete` / `_fail`（无终态检查，可重复写）。
  - `harness/core/scheduler/base.py:208-266` `run()`（watchdog、finally 清理）。
  - `harness/core/fold.py` `RunStatus`（completed/failed）。
  - `harness/storage/event_store.py` `append_event`。

## 2. 问题背景

日志证据：
- `watchdog_verify_stderr.log:84-86`：RunFailed 已写，但 `pending_calls=1`——主 Run 终态后仍有异步调用未回收。
- `harness.log` 多次出现 `Plan complete — status=failed failures=0` 与 `status=completed failures=0`（计数/状态不一致属 S11 范围，本步管终态）。
- 潜在：watchdog/用户取消/熔断并发调用 `_fail` 会写**重复 RunFailed**；终态之后理论上仍可写 RunCompleted（迟到事件）。

根因：`_fail`/`_complete` 无终态守卫；事件写入无 run 终态拦截；终态与资源回收解耦。

## 3. 为什么这么做

- C-05：终态幂等是 S10（取消/迟到拦截）的前置。先保证"每个 Run 只有一个终态事件"，再谈取消。
- D-06：Run 终态之后不得再产生迟到副作用或事件（INDEX 验收项 9）。
- AGENTS.md 约束 3/§6.1：受信组件异常必须转结构化事件，且不静默。

## 4. 做之前先检查影响范围

- `_fail` 调用点（全库 grep）：watchdog、cancel、breaker、confirm 超时、`_handle_dag_confirmations`、`_plan_cycle` 多处。
- `_complete` 调用点：`_finalize_with_summary`、analysis-only 路径、empty plan 路径。
- `append_event` 消费方：所有事件写入。**注意 L-03**：只能对 run 事件流拦截，workspace/conversation 审计事件复用同一表不得误伤。
- 测试：`tests/test_scheduler.py`、`tests/test_lifecycle.py`、`tests/test_monitoring.py`、`tests/test_api.py`。
- **并发**：`_fail` 可能在 `asyncio` 多个 task 中并发调用（如 watchdog task + 主循环 + 取消 handler），须用锁或折叠检查保证单终态。

## 5. 期望达到的目标

- `_fail` / `_complete` 幂等：进入前 fold 当前状态，若已 terminal 则**直接返回**（或写幂等标识，不重复写终态事件）。
- 终态后事件拦截：run 事件流的 `append_event` 增加终态守卫——Run 已 terminal 后，除审计/收尾事件外拒绝写入；实现为**运行态软检查**（Scheduler/执行路径检查 `_is_terminal` 后拒绝），**不改为 EventStore 全局硬拒绝**（L-03）。
- 迟到事件检测：记录 `RunCompleted/RunFailed` 写入时的 `seq`；终态后任何工具/计划事件尝试写入 → 记结构化 `LATE_EVENT_REJECTED`（新增事件类型或复用告警）供观测。
- `pending_calls` 语义保留给 S10 做硬性清理断言（本步只保证终态唯一）。

## 6. 实现要点

```python
async def _fail(self, run_id: str, error: str) -> None:
    async with self._resume_lock:                       # 已有锁，防并发
        events = await self.store.get_events(run_id)
        state = fold_events(events)
        if state.status in (RunStatus.FAILED, RunStatus.COMPLETED):
            _sched_breaker.warning("[breaker] _fail ignored for run=%s (already %s)", run_id, state.status.value)
            return                                          # 幂等：不重复写终态
        ...  # 原有 RunFailed 写入逻辑
```

- `_complete` 同样加守卫。
- 迟到事件拦截：在 `scheduler/plan.py` 执行循环与 `dag_executor` 的每步写入前检查 `_is_terminal`（读事件折叠或维护内存 terminal 标记）；tool 完成回调若发现已 terminal → 拒绝写入并记录。
- 新增事件类型（若决定独立）：`LATE_EVENT_REJECTED`（payload: run_id, seq, event_type, reason）——注册到 `PAYLOAD_MODEL_MAP`。
- **禁止事项**：
  - 禁止在 `EventStore.append_event` 全局加 run 终态硬拒绝（L-03 误伤审计流）。
  - 禁止在 `_fail` 内再次触发 `_fail`（递归）。
  - 禁止静默吞掉重复终态尝试（必须记录，便于观测）。

## 7. 验收标准

1. 新增测试 `tests/test_terminal_guard.py`：
   - 已 FAILED 的 Run 再次 `_fail` → 不新增 RunFailed 事件。
   - 已 COMPLETED 的 Run 再 `_complete` → 不新增 RunCompleted。
   - 终态后尝试写 ToolCompleted / DagStepCompleted → 被拒 + 结构化记录（测试要求 16）。
   - 终态后写 Conversation/Workspace 审计事件 → 不受影响（L-03）。
   - 并发 `_fail`（多 task）→ 事件流只有一个 RunFailed。
2. `pytest tests/test_scheduler.py tests/test_lifecycle.py tests/test_api.py tests/test_event_store.py` 回归全绿。
3. 事件流可重放：任何 Run 最多一个终态事件（RunCompleted 或 RunFailed）。

## 8. 这么做的后果

- **对 S10**：取消/宽限期/pending 断言基于"单终态"建立，不会重复写入。
- **对 S11**：终态唯一 → 失败计数可从事件折叠获得（不再依赖 `failures` 计数器）。
- **对 S12**：验收项 9（终态后无迟到事件）、16（无重复终态）由本步达成。
- **行为变化**：极端情况下 watchdog 与正常完成竞争 → 先到先终态，后到被拒（预期）。
