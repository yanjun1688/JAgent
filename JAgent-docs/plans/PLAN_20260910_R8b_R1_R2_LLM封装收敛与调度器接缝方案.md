## 0.0 裁决结果（2026-09-12）—— R1/R2 以"删除 fallback"解决

owner 裁决：**不采用 §2.2 / §3.2 的方案 A/B**，改为**删除生产 fallback**（架构减法）：

- planner 重试耗尽产不出合法计划 → `PlanningExecutorScheduler` 直接写结构化 `RunFailed`（`"Planner failed to produce a valid plan"`），**不再 `new` 独立 `AgentLoopScheduler`**。
- 由此 **R2（嵌套调度器：双 deadline / 控制信号断裂 / 双层 cleanup）与 R1（serial 弱完成路径）在生产同时消失**；`AgentLoopScheduler` 类保留，仅供 evaluation/scripts 显式装配（未来 ADR-013 反应式模型按 `grounding` 选择调度器，而非降级）。
- 自愈由既有 **步骤级局部修复（F-6，默认开启）+ 全局 revise** 承担；超限走完成门诚实失败（no fake-green）。
- 已实现 + 回归：`plan.py` 删除 `_get_or_fallback`；`SchedulerConfig.local_repair_enabled` 默认 True 且候选工具由注册表派生（删除手工白名单 `local_repair_allowed_tools` 与 `HARNESS_LOCAL_REPAIR*` env，消除"第二套只读判定"）；失败预算收敛为单一 `run_attempt_budget`（合并旧 `max_iterations` + `max_consecutive_failures`）；新增 `tests/test_planner_failure_no_fallback.py`；全量 **1522 passed / 2 skipped**。
- §2.2/§3.2 的方案 A/B 与 §2.3/§3.3 的 owner 待决点**作废**（不再需要 serial 完成语义裁决）。

## 1. R8-b：LLM 外围 6+1 封装语义收敛 —— 任务描述

### 1.1 要收敛什么（当前证据，均在 R8-a 之后原样存在）

- `AgentPhase.SERIAL_THINK`（`system_prompt.py:347`，文本 :207-239）注册后**无消费方**；实际使用 `SERIAL_THINK_FN/_TEXT`（`agent_kernel.py:187,196`），与 plain `_SERIAL_THINK_PROMPT` 约 90% 重复。

### 1.2 语义边界（哪些"不一致"是有意为之、不得顺手统一）

- **③ classify 的保守放行**：受信门先跑 `intent_requires_tools`（classify.py:48-57,125-130）；LLM 异常→needs_tools=True 是**受信安全默认**（宁可多跑工具层 fail-closed 校验），属设计意图，只做 run_id/计时收敛，不改判定方向。
- **⑦ llm_judge 异类**：评测域无 run_id/deadline 是合理豁免；不纳入 run deadline 语义统一，仅确认 parse 已共享、异常→None 文档化。
- **取消（CancelledError）**：统一原则是 `BaseException`（含取消）不得被封装吞掉——与 #19/#22、ADR-014 语义一致。R8-b 收敛的是 **LLM 传输/解析异常的兜底方向与 run_id/计时上报口径**，不是取消语义。

### 1.3 任务拆解（建议一次任务描述，可拆提交）

1. **T-R8b-1 run_id 上报缺口**：contract extractor（④:161）、episode 摘要（⑤）、serial kernel think（⑥，经 loop）补 run_id 透传 → `llm_client.chat(..., run_id=...)` 统一打标。契约抽取的 run_id 需从 `classify.py:79` 构造点一路透传（受信边界内，纯接线）。

## 2. R1：serial 完成路径绕过终态守卫 —— 只出方案

### 2.1 现状（代码已核实）

- `loop.py:182-188`（direct_answer）与 `:193-197`（LLM 选 stop）**直写** `RUN_COMPLETED`，不经 `BaseScheduler._complete()`（`base.py:645-685`）。
- 因此无 `_resume_lock` 终态幂等守卫（`base.py:653-659`），`RunCompletedPayload` 不带 `all_normal/unmet_step_ids/deliverable_*`（折叠出默认值 `completion_evidence`）。
- serial 轨道全文件 grep `CompletionVerdict` = 0、不读 `state.delivery_contracts` → API 提交的 `required_operations` 在 serial 不构成完成门。
- 同类：确认循环直写 `RUN_PAUSED`（`base.py:1009-1013`），不经带 `allow_after_terminal` 的 `_append_run_event`（`base.py:590-624`）。
- 可达性：生产 `deps.py:160` 只装配 `PlanningExecutorScheduler`；serial 生产可达仅经 R2 fallback，其余为 evaluation/scripts。

### 2.2 方案选项

**方案 A（推荐）：serial 完成口复用 `_complete()` / `_append_run_event`**
- `loop.py` 两处直写改走基类受信完成口：构造 `CompletionVerdict`（serial 语义：无 step 链 → `all_normal=True` 的合理解释需定义，见 2.3）后调 `self._complete(...)`；`RUN_PAUSED` 直写改走 `self._append_run_event(..., allow_after_terminal=True)`。
- 收益：终态幂等守卫与 `completion_evidence` 双维证据对 serial 生效；消除"第二条弱完成路径"。
- 成本：serial 需要定义"完成证据"的语义（serial 无 step_id，`unmet_step_ids` 为空、`all_normal` 需从 LLM stop 语义推导）；需保证 evaluation/scripts 既有断言不破（它们读 serial 的事件流）。

**方案 B：收敛到单一完成门（与 R2 联动）**
- 若 R2 走"同实例降级 serial 模式"（见 §3 方案 B），serial 完成本就落在 planning scheduler 实例内，统一走 planning 的完成门即可 —— R1 方案 A 降级为 R2 方案的子步骤。二者需同批设计、可分批实现（先 A 后 R2-B，避免两套中间态）。

### 2.3 必须由 owner 裁决的点

1. serial 无 step 链时 `all_normal`/`deliverable_status` 的**语义定义**：建议 `all_normal=True`（无异常 step）+ `deliverable_status="unverified"`（serial 未消费 contracts），与 planning 的"failed 即非 all_normal、有交付契约才判 deliverable"口径对齐，杜绝伪造假绿。
2. serial 是否也要对 `required_operations` 生效？—— 若 yes，串行轨道需引入交付契约折叠/校验，范围显著扩大；**建议本批只做"走受信完成口 + 证据字段口径化"，不引入 serial 完成门**（把"serial 消费 contracts"列为 R8-b 或独立项，避免本批膨胀）。

## 3. R2：planner 失败回退 serial —— 只出方案

### 3.1 现状（代码已核实）

- `plan.py:1148-1161` 在重试耗尽后 `new` 独立 `AgentLoopScheduler`（独立对象/控制字典），同 store/executor/config，复用同一 config，未传 `run_end_cb`（走默认 no-op）。
- 后果：① 双 watchdog/deadline（`base.py:239-252` 每实例一份）；② fallback 期间 pause/resume/confirm 断裂（API 持外层实例 `deps.py:56,160-176`，`routes.py:443/475/557/643` 解析外层，内层 `_wait_for_resume` `base.py:1102-1132` 等内层自己的 Event）；③ cleanup/reaper 双层执行（`base.py:289-332` 两层各跑一次，`deps.py:173` 的 `cleanup_run_resources` 只随外层跑）。

### 3.2 方案选项

**方案 B（推荐）：同实例降级 serial 模式（消除嵌套实例）**
- 不 `new` 新调度器；在**当前 planning scheduler 实例内**切换执行模式：`_plan_cycle` 检测 planner 重试耗尽 → 在实例内以 serial 语义续跑（复用同一 store/executor/control 字典/deadline/cleanup/`run_end_cb`）。
- 收益：单 deadline 预算、pause/resume/confirm 天然同控（同一 `_pause_events/_confirm_events`）、cleanup 单次；R1 弱完成路径在实例内统一走同一完成口。
- 成本：需把 serial 循环逻辑从"独立 AgentLoopScheduler 类"抽成**实例内可复用方法/状态机**（`loop.py` 的 ReAct 循环迁移或薄封装）；是调度器接缝的实质重构，触碰面较大（需动 `plan.py`/`loop.py`/`base.py` 的组合关系），宜独立任务描述 + TDD。

**方案 A（保守，推荐作为过渡或否决 B 时的回退）**：修嵌套但不改状态机 —— fallback 时把外层 scheduler 的控制字典/event/done 引用**注入**内层 serial（传 `_pause_events`/`_confirm_events`/`run_end_cb` 共享同一份），不消除双 deadline 但消除控制信号断裂与 run_end_cb 丢失。成本低、风险小，但保留双 watchdog/双 cleanup 的技术债。

### 3.3 必须由 owner 裁决的点

1. 选 A（低风险修补，留双 deadline 债）还是 B（同实例降级，治本但重构面大）？
2. 若 B：serial 循环抽为实例内状态机的归属（复用 `AgentLoopScheduler.run` 逻辑还是迁移到 planning 实例方法）；与 R1 方案的关系（建议 R1-A 先落、R2-B 随后，见 §2.2）。
3. fallback 的语义归属：这是 planner 兜底还是应抽象为"planner 失败 → 状态机统一处理"？若后者，需避免引入 Workflow Engine（与架构约束冲突）——以**状态机内的分支**而非**编排器**表达。
